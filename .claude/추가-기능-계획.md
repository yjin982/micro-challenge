# 추가 기능 계획: 완료 메모, 미션 제안

2026-10-27 작성. 2026-10-28에 화면 설계 보드([밍기적 챌린지 화면 설계-메모,미션제안.pdf](<밍기적 챌린지 화면 설계-메모,미션제안.pdf>), 22쪽)를 보고 결정을 다시 정했다(1-8, 2-6). 이 문서에서 '보드 N쪽'은 이 PDF의 쪽 번호다. 보드와 이 문서가 다르면 **이 문서의 결정**을 따른다(보드를 그린 뒤 고친 것이 있다).

로그인 흐름 개편을 `main`에 합친 뒤(커밋 `e6ed5b6`)의 다음 작업이다. 순서는 **1. 완료 메모 → 2. 미션 제안**이다. 2는 1을 마친 뒤 만든다. 기록 모아 보기([로그인 계획](로그인-흐름-계획.md) 10단계)는 이 문서와 따로다. 작업 브랜치는 `feat/entry-note`.

## 1. 완료 메모(미션을 마치며 한 줄 남기기)

### 1-1. 왜 필요한가

지금은 '완료했어요!'를 누르면 바로 도장이 찍힌다. 몸을 쓰는 미션은 그걸로 충분하지만, 머릿속에서 끝나는 미션은 해냈다는 감각이 약하다.

- 인지/생각: "10초 동안 아무 생각 안 하기 도전"(E088). 해 봤는지, 어땠는지 남길 곳이 없다
- 감정/자기표현: "지금 기분 한 단어로 표현"(E091), "나에게 '요즘 뭐가 제일 좋아?' 물어보기"(E101). 떠올린 단어나 답을 적어야 완료한 느낌이 난다
- 몸/행동: "팔꿈치를 구부렸다 펴기"(E029)도 느낌이나 한 방법을 적어 둘 수 있다

그래서 완료할 때 짧은 글을 남길 수 있게 한다. **쓰지 않아도 완료된다.** 미션 200개가 7개 분류에 걸쳐 있으므로 대화상자의 제목과 자리 글(placeholder)은 어느 분류에도 어색하지 않은 공통 문구 하나로 둔다.

### 1-2. 동작

#### 홈에서 완료할 때(보드 5–9, 15–16쪽)

```text
도전중 카드 → '완료했어요!' → 메모 대화상자
   ├─ (쓰거나 비워 두고) '완료하기' 또는 Enter → 완료 요청(메모 포함) → 대화상자 닫힘 → 지금과 같은 도장 연출
   └─ '취소' / Esc / 바깥 → 대화상자만 닫힘(완료되지 않음, 쓰던 글은 버린다)
```

- 메모는 비워도 된다. 앞뒤 공백만 있으면 비운 것으로 본다
- 줄바꿈은 받지 않는다. Enter는 '완료하기'와 같다. 붙여 넣은 글의 줄바꿈은 공백 하나로 바꾼다. 입력창은 긴 글을 화면 안에서 줄을 감아 보여준다(보드 6–7쪽)
- 글자 수 상한 **200자**. 입력창 아래 오른쪽에 `0 / 200`. 200자를 넘으면 입력창 테두리와 숫자가 빨간색이 되고 '완료하기'가 비활성(흐린 초록)이 되어 제출할 수 없다(보드 7쪽). 입력 자체는 막지 않는다(붙여 넣은 뒤 줄여서 낼 수 있게)
- 완료 요청이 실패하면 대화상자를 닫지 않고 입력창 아래에 빨간 안내(예: "완료하지 못했어요. 인터넷 연결을 확인하고 다시 눌러 주세요.", 보드 8쪽). 쓰던 글이 남아 있어야 한다
- 완료 취소는 여전히 없다. 메모를 지워도 완료는 그대로다
- 모바일 스와이프는 다시 뽑기만 하므로 그대로 둔다
- 완료 뒤 홈의 완료 카드에 메모를 보여준다: 미션 문구 아래 점선, 연필 아이콘, 메모(보드 9쪽 모바일 완료 화면, 16쪽 데스크톱 왼쪽 카드). 연속 달성 화면(모바일)과 최근 기록에는 보여주지 않는다

#### 기록 화면 `/records`(보드 10–13, 17쪽)

- 완료한 날의 상세 카드: 도장 아래 점선, 연필 아이콘과 메모, 오른쪽 아래 테두리 버튼 '수정'(연필)·'삭제'(휴지통, 빨간 글자)(보드 10, 17쪽)
- 메모가 없으면 점선 아래 넓은 테두리 버튼 '한 줄 남기기'(연필)(보드 11쪽). 완료한 날이면 지난 날도 나중에 쓸 수 있다
- 수정·한 줄 남기기는 완료할 때와 같은 대화상자, 주 버튼만 '저장'(보드 12쪽)
- 삭제 확인(보드 13쪽): 고민하는 티라노(`tyrano-thinking`), "이 메모를 지울까요?" / "미션 완료와 도장은 그대로예요.", 빨간 '메모 지우기', 테두리 '취소'. 첫 포커스는 '취소'
- 고칠 수 있는 것은 **메모 글뿐**이다. 미션, 완료 시각, 도장, 완료 여부는 바꿀 수 없다
- 완료하지 않은 날(오늘 도장 전, 쉬어 간 날)에는 메모가 없다
- 오늘 메모를 기록 화면에서 고치면 홈에 돌아갔을 때 새 내용이 보여야 한다(홈은 들어올 때 오늘 상태를 다시 불러온다)

### 1-3. 문구(결정)

| 자리 | 문구 |
| --- | --- |
| 대화상자 제목 | 오늘의 기적, 한 줄 남겨 볼까요? |
| 입력창 자리 글 | 무엇이든 좋아요. 비워둬도 완료돼요. (모든 미션 공통. 분류별 문구는 쓰지 않는다) |
| 글자 수 | `n / 200` |
| 주 버튼 | 완료하기(기록 화면에서는 저장) |
| 보조 | 취소 |
| 완료 실패 | 완료하지 못했어요. 인터넷 연결을 확인하고 다시 눌러 주세요. (그 밖의 실패는 지금 홈의 오류 문구 규칙을 따른다) |
| 기록 상세(메모 없음) | 한 줄 남기기 |
| 삭제 확인 | 이 메모를 지울까요? / 미션 완료와 도장은 그대로예요. / 메모 지우기 / 취소 |

- 메모 대화상자에는 마스코트를 넣지 않는다. 안내 문장도 따로 두지 않는다(자리 글이 안내를 겸한다)

### 1-4. DB 설계(결정: 컬럼 추가)

`daily_entries`에 컬럼을 더한다. 새 테이블을 만들지 않는다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| **가. `daily_entries`에 `note`, `note_updated_at` 추가(채택)** | 완료와 1:1이라 구조가 단순하다. 기존 RLS("본인 행 읽기"), 계정 삭제 cascade, `get_month` 조회를 그대로 쓴다 | 메모 이력(예전 글)은 남지 않는다 |
| 나. 새 테이블 `entry_notes(user_id, date, note, …)` | 메모만 따로 관리·확장(여러 개, 이력)하기 쉽다 | RLS·외래 키·조인이 늘어난다. 하루 한 개라 얻는 것이 적다 |

```sql
-- 새 마이그레이션(예: 2026MMDD000000_entry_note.sql). SQL Editor에서 실행한다
alter table public.daily_entries
  add column note text check (note is null or (note <> '' and note !~ '[\r\n]' and char_length(note) <= 200)),
  add column note_updated_at timestamptz,
  -- 메모는 완료한 날에만
  add constraint daily_entries_note_needs_completion check (note is null or completed_at is not null);

-- 입력 정리: 줄바꿈·탭 등 공백 문자를 공백 하나로, 연달은 공백은 하나로, 앞뒤 공백 제거, 비면 null
create or replace function public.clean_note(p text)
returns text language sql immutable as $$
  select nullif(btrim(regexp_replace(coalesce(p, ''), '[\s]+', ' ', 'g')), '')
$$;
```

- 상한 200자: 화면이 막고(1-2), DB 함수가 정리한 글(`clean_note` 결과)이 200자를 넘으면 `INVALID_INPUT`, 제약이 마지막으로 막는다. 화면을 거치지 않는 요청도 막힌다
- 글자 수는 Postgres `char_length`(유니코드 문자 단위)와 같게 센다. 화면에서 `value.length`(UTF-16 단위)를 쓰면 이모지가 2자로 세어져 어긋나므로 `[...value].length`(코드 포인트)로 센다
- 줄바꿈은 화면이 막고, `clean_note`가 공백으로 바꾸고, 제약이 마지막으로 막는다
- 화면은 글자로만 그린다(React가 이스케이프한다). HTML로 넣지 않는다
- 계정 삭제·익명 정리(180일) 때 행과 함께 지워진다. 따로 할 일이 없다

### 1-5. DB 함수와 API

| 바뀌는 것 | 내용 |
| --- | --- |
| `complete_today(p_date date, p_note text default null)` | 기존 함수를 지우고(`drop function public.complete_today(date)`) 인자를 더해 다시 만든다. 인자가 바뀌면 Postgres는 다른 함수로 보므로 지우지 않으면 두 개가 생긴다. 기본값이 있어 메모 없이 부르던 화면도 그대로 동작한다. 실행 권한(`revoke`/`grant`)도 새 서명으로 다시 준다 |
| `set_note(p_date date, p_note text)` 새 함수 | 본인(`auth.uid()`)의, **완료한** 날의 메모만 고친다. `clean_note` 결과가 null이면 삭제. 행이 없거나 완료 전이면 `NOT_FOUND`. 돌려주는 값 `{ date, note, noteUpdatedAt }` |
| `today_state` | `note`(오늘 메모, 홈 완료 카드용)를 더한다 |
| `get_month` | `days[]`에 `note`를 더한다 |

| API | 요청 | 응답 |
| --- | --- | --- |
| `POST /api/today/complete`(기존) | `{ date, note? }` | 지금과 같은 오늘 상태(+ `note`) |
| `PATCH /api/records/note`(새, 7번째 API) | `{ date: "YYYY-MM-DD", note: string \| null }`. `null`이나 빈 글이면 삭제 | `{ date, note, noteUpdatedAt }` |

- 기존 규칙 그대로: Route Handler → `supabase.rpc()` → security definer 함수. 테이블 쓰기 정책은 두지 않는다
- `types/api.ts`(`TodayState.note`, `MonthRecords.days[].note`, 새 응답 타입), `ErrorCode`에 `NOT_FOUND`(404), `lib/api-error.ts` 문구, `handleRpc`가 받는 함수 목록, `pnpm gen:types`
- 확인 SQL `supabase/tests/entry-note.sql`(`delete-account.sql`처럼 임시 사용자로 확인 후 되돌림): 메모와 함께 완료, 빈 메모·공백만은 null, 줄바꿈이 공백으로 바뀜, 200자는 통과·201자는 `INVALID_INPUT`, 완료 전 날·없는 날은 `NOT_FOUND`, 삭제, 다른 사용자 행은 못 고침, 완료 안 한 행에 메모를 넣으면 제약에 걸림, 메모 없이 부르던 `complete_today(p_date)`도 동작

### 1-6. 화면 컴포넌트

| 컴포넌트 | 위치 | 내용 |
| --- | --- | --- |
| `NoteDialog` | `components/ui/` 또는 `components/home/` | 완료·수정·한 줄 남기기가 함께 쓰는 대화상자. 제목, 입력창(공통 자리 글), 글자 수 `n / 200`, 실패 안내, 주 버튼('완료하기'/'저장', 200자를 넘으면 비활성), 취소. 마스코트 없음 |
| 홈 완료 연결 | `components/home/` | '완료했어요!' → `NoteDialog` → `api.complete(date, note)` → 지금의 도장 연출(`celebrate`) |
| 홈 완료 카드의 메모 | `components/home/DoneCard.tsx` 등 | 메모가 있으면 점선·연필 아이콘·메모(없으면 아무것도 없음) |
| 기록 상세의 메모 | `components/records/RecordDetail.tsx` | 메모 보기, 한 줄 남기기·수정(`NoteDialog`)·삭제 |
| 삭제 확인 | `SketchDialog` | `tyrano-thinking`, 첫 포커스 "취소"(`data-autofocus`), 빨간 '메모 지우기'(`Button` `danger`) |
| 처리방침 변경 안내 | `components/home/` | 홈 위쪽 노란 띠(보드 14, 18쪽). 1-7 |

- 입력창: 줄을 감아 보여주는 `textarea`(높이 자동, 넘치면 안에서 스크롤)에서 Enter를 '제출'로 바꾸고, 붙여 넣은 줄바꿈을 공백으로 바꾼다. 한글 입력 조합 중의 Enter(`isComposing`)는 제출로 보지 않는다
- 글자 수: `aria-live="polite"`. 넘으면 숫자·테두리 빨간색(`sunday`), 입력창 `aria-invalid`, 주 버튼 `disabled`. Enter로 제출할 때도 같은 조건을 본다
- 열리면 입력창에 포커스. 입력창 라벨은 대화상자 제목과 연결한다
- 지금의 [SketchDialog](../components/ui/SketchDialog.tsx)는 마스코트와 안내 문장을 꼭 받는다. 둘 다 선택으로 바꾸고, 입력창을 children으로 넣어 첫 포커스를 입력창에 준다(`data-autofocus`)
- 모바일 화면 키보드가 올라오면 대화상자가 가려지지 않게(`dvh`, 입력창 쪽으로 스크롤) 확인한다(보드 6쪽)
- 아이콘: 연필, 휴지통을 [icons.tsx](../components/ui/icons.tsx)에 더한다

### 1-7. 처리방침 변경과 알림(결정: 추천안)

사용자가 직접 쓴 글을 새로 저장하므로 [처리방침](../components/legal/documents.ts)을 고친다.

- 1절 '서비스 이용 기록'에 "미션을 마치며 직접 남긴 메모(남긴 경우)"
- "메모는 본인만 볼 수 있고, 문의에 답하거나 법에 따라야 하는 경우 말고는 운영자가 열어 보지 않습니다" 한 줄
- 9절(지금) "내용이 바뀌면 시행 7일 전부터 서비스 안에서 알립니다" → (변경) "내용이 바뀌면 서비스 안에서 알립니다. 수집하는 정보가 늘거나 이용자에게 불리하게 바뀌는 경우에는 시행 7일 전부터 알립니다"
- 시행일 = 메모 기능 배포일. 메모는 쓰고 싶을 때만 남기는 선택 항목이라 배포와 함께 바꾸고, 9절 문구 수정도 이번 변경에 넣는다
- 안내(보드 14, 18쪽): 홈 위쪽 노란 띠 "개인정보처리방침이 바뀌었어요(완료 메모 추가)" + '보기'(`/privacy`) + ✕. 닫은 것은 브라우저에 기억한다(`localStorage`, 기기마다). 시행일 7일 뒤에는 코드에서 띄우지 않는다
- 이 판단은 법률 자문이 아니다. 정식 공개 전에 한 번 더 확인한다

| 글자 수 | **200자 상한**. 입력창 아래 `0 / 200`, 넘으면 테두리 빨간색 + 주 버튼 비활성, 서버도 같은 상한(2026-10-28. 그 전 결정 '제한 없음' → '2,000자'에서 바꿨다) |

## 2. 미션 제안(완료 메모 다음에 만든다)

기획서·서버 설계의 '4단계(보류)'에서 출발해, 보드 2·4쪽(계정 메뉴), 19–21쪽(미션 제안하기), 22쪽(관리자)과 2026-10-28 결정에 맞게 고친다. 화면 이름은 '미션 제출'이 아니라 **'미션 제안하기'**다.

### 2-1. 기존 설계 요약(서버 설계 부록 A~C)

- `submissions`(id, user_id → `auth.users` on delete cascade, text 5~40자, `normalized_text`(공백·문장부호 제거, 소문자), difficulty, status pending/approved/rejected, mission_id, created_day, created_at, reviewed_at, `unique(user_id, normalized_text)`)
- `admins(user_id)`, `is_admin()`, 승인 번호 시퀀스 `user_mission_seq`(S0001…)
- 함수: `submit_mission`(하루 3개, 기존 미션·내 제출과 중복 거절), `admin_list_submissions`, `admin_approve`(문구·난이도 고쳐서 승인 → `missions`에 S번호로 추가, `source = 'user'`), `admin_reject`
- RLS: submissions는 본인 행 읽기만, 쓰기는 함수로만. admins는 정책 없음

### 2-4. 처리방침·약관에 더할 것

- 처리방침 1절: 제안한 미션 문구, 처리 상태, 반려 사유
- 약관: 제안한 문구는 승인되면 서비스의 미션으로 다른 이용자에게 보이고, 운영자가 고칠 수 있으며, 계정을 지워도 미션으로 남는다(약관 7절 '미션 문구의 권리는 운영자에게'와 맞춘다). 개인정보나 남을 불편하게 하는 내용은 반려한다
- 변경 알림: 수집하는 정보가 늘므로 1-7에서 고친 9절대로 **시행 7일 전**부터 알린다. 미션 제안을 열기 7일 전에 처리방침·약관을 먼저 바꾸고 홈 안내 띠를 띄운다

### 2-5. DB 변경 초안(부록 A~C를 고쳐 새 마이그레이션으로)

```sql
-- 부록 A의 normalize_text, admins, is_admin, user_mission_seq는 그대로
create table public.submissions (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references auth.users (id) on delete cascade,
  text            text not null check (char_length(text) between 1 and 200),
  normalized_text text generated always as (public.normalize_text(text)) stored,
  difficulty      text not null check (difficulty in ('easy', 'challenge')),
  status          text not null default 'pending' check (status in ('pending', 'approved', 'rejected')),
  mission_id      text references public.missions (id),
  category        text,                       -- 승인할 때 관리자가 고른 분류(missions에도 넣는다)
  review_note     text,                       -- 반려 사유(비워도 됨)
  created_at      timestamptz not null default now(),
  reviewed_at     timestamptz,
  unique (user_id, normalized_text)
);  -- created_day(하루 제한용)는 없앤다
```

- 분류 값은 지금 미션의 7개(몸/행동, 인지/생각, 감정/자기표현, 환경 상호작용, 이상한 행동/밈, 디지털/습관, 도전적) 중 하나로 검사한다
- 내 제안 목록(`GET /api/submissions`)은 문구, 날짜, 난이도, 상태, 반려 사유를 돌려준다
- `pick_mission`은 `is_active`인 미션 전체에서 뽑으므로 승인된 S번호 미션은 바로 후보가 된다. 바꿀 것 없다
- 관리자 등록: `insert into public.admins (user_id) values ('<관리자 Google 계정 user id>');`
- API 6개: `GET /api/submissions`, `POST /api/submissions`, `DELETE /api/submissions/[id]`(취소), `GET /api/admin/submissions?status=`, `POST /api/admin/submissions/[id]/approve`, `POST /api/admin/submissions/[id]/reject`
