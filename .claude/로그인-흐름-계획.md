# 로그인 흐름 개편 계획

2026-10-19 작성, 2026-10-21 수정(로그인 수단을 **익명 + Google**로 확정, 이메일 로그인은 개발 환경 전용, 기존 계정 로그인 확인 문구와 조건 정리. 이어서 [콜백 실패 처리](#콜백-실패-처리2026-10-21-확인)와 Redirect URLs 설정 보완, Google 버튼은 공식 생성기 코드로, 익명 계정 메뉴는 "Google로 기록 지키기" 하나로, 개인정보 안내·계정 삭제는 범위 밖으로). (2026-10-27) 4A·4B·4C·4D까지 구현하고 처리방침·약관 빈칸도 채웠다(`feat/google-login` 푸시 완료, `main`에는 아직 합치지 않음). 같은 날 보안 점검으로 `safeNext`를 고치고, `main`에 Next.js 16.4.3 보안 업데이트를 넣어 이 브랜치에 합쳤으며, pnpm을 12.8.1로 고정했다. 남은 것은 5단계(Google 계정 시나리오는 사용자), `main` 병합·배포, 6단계(익명 정리 SQL, Google 앱 게시), 7단계(기획서·서버 설계)다. 2026-10-22 기준으로 [4. 작업 단계](#4-작업-단계)의 0~4단계를 구현했다(커밋 `52d2e8d`, 브랜치 `feat/google-login`). 같은 날 화면 설계가 개정되어(계정 메뉴, 설정, 처리방침·약관, 기록 모아 보기, [화면 설계 개정](#화면-설계-개정2026-10-22)) 남은 순서를 4A단계(계정 메뉴 개편) → 4B(설정) → 4C(계정 삭제) → 4D(처리방침·약관) → 5(시나리오 테스트·배포) → 6(공개 준비) → 7(문서) → 10(기록 모아 보기, 별도 브랜치)으로 다시 짰다.

화면은 '밍기적 챌린지 화면 설계' 캔버스의 **로그인: 익명 + Google** 줄(보드 9개)을 기준으로 한다.

### 이메일 가입을 하지 않는 이유

이메일 가입은 메일 인증이 사실상 필요한데, 무료로는 실제 사용자에게 메일을 보내기 어렵다(Supabase 문서 기준, 2026-10-21 확인).

- Supabase 기본 메일 서버는 **프로젝트 팀원으로 등록된 주소에만** 보낸다. 다른 주소는 `Email address not authorized`로 실패한다
- 발송량은 **프로젝트 전체에서 시간당 2통**이다(가입 인증·비밀번호 재설정·이메일 변경 메일을 모두 합친 수)
- 2026-06-03 이후 만든 무료 프로젝트는 기본 메일 서버를 쓰는 동안 메일 템플릿을 고칠 수 없다(외부 SMTP를 연결하면 가능)
- 무료 외부 SMTP(Brevo 하루 300통, Resend 하루 100통 등)는 아무에게나 보내려면 보통 **내 도메인 인증**이 필요하다. 도메인 구입과 DNS 설정까지 해야 한다

Google 로그인은 인증을 Google이 맡으므로 메일 서버, 인증 메일 화면, 비밀번호 찾기가 모두 필요 없다. Supabase 무료 플랜에서 쓸 수 있다.

### 이메일 테스트 계정(개발 환경에서만)

> 2026-10-26에 `/login`을 지워 이 절은 더 이상 해당하지 않는다. `supabase/test-users.sql`의 계정은 DB에 남아 있지만 화면에서 로그인할 수 없다. Supabase의 Email 제공자는 이제 꺼도 된다(사용자 판단).

[supabase/test-users.sql](../supabase/test-users.sql)의 테스트 계정 3개(기록 없음, 5일 연속, 기록 2개)로 화면 상태를 확인할 수 있도록 이메일 로그인을 개발 환경에만 남긴다(2026-10-21 결정).

- 운영(`NODE_ENV !== "development"`)에서는 proxy가 `/login`을 없는 경로로 바꿔 404를 준다. 페이지의 `notFound()`도 그대로 둔다(루트 `loading.tsx` 때문에 페이지에서 부르면 상태 코드가 200으로 남아서 proxy에서 막는다, 2026-10-22). 배포된 앱에는 이메일 로그인 화면이 없다
- 진입점: 개발 환경에서만 `/welcome` 맨 아래에 작은 링크 "개발용 이메일 로그인"을 둔다(보드에는 없다). 주소로 직접 들어가도 된다
- [LoginForm](../components/auth/LoginForm.tsx)과 `lib/api.ts`의 `signInWithEmail`은 남긴다. 로그인 뒤에는 `next`(기본 `/`)로 간다
- Supabase 설정
  - Email 로그인은 켜 둔다
  - **가입 메일 인증(Confirm email)도 켜 둔다.** 가입 화면은 없지만 공개 키로 `signUp` API를 직접 부르면 이메일 계정을 만들 수는 있다. 인증이 켜져 있으면 그렇게 만든 계정은 인증 메일을 받지 못해(기본 메일 서버는 팀원 주소만) 로그인할 수 없다. SQL로 만든 테스트 계정은 이미 인증된 상태라 상관없다
  - "Allow new users to sign up"(회원가입 허용)은 끄지 않는다. 이메일만이 아니라 프로젝트 전체 설정이라 Google 첫 로그인(가입)도 막힐 수 있다
- 이메일 계정은 계정 메뉴에서 Google 계정과 같은 '계정' 상태로 보여준다(프로필 사진 대신 이메일 첫 글자)

## 배경

지금은 앱을 열면 [AnonymousSession](../components/auth/AnonymousSession.tsx)이 바로 익명 계정을 만들고, 이메일 계정은 주소로만 들어가는 `/login`에서 쓴다(테스트 계정용, 개편 뒤에는 개발 환경에서만). 처음 접속할 때(세션이 없을 때) 익명으로 시작할지 Google로 계속할지 고르는 시작 화면을 둔다.

### 세 가지 상태 구분

| 상태 | 확인 방법 |
| --- | --- |
| 세션 없음(최초 접속, 로그아웃 뒤) | `getClaims()` 결과가 `null`, `sb-…-auth-token` 쿠키 없음 |
| 익명 | 세션이 있고 `user.is_anonymous === true`(JWT 클레임 `is_anonymous`에도 있음) |
| Google 계정 | 세션이 있고 `is_anonymous === false` |

세션이 쿠키에 있어 브라우저와 서버(`proxy.ts`, Route Handler) 모두에서 판단할 수 있다.

### 지금 구조에서 막히는 점

다음 두 곳이 익명 계정을 자동으로 만들어서 "세션 없음" 상태가 화면에 닿기 전에 사라진다.

1. [AnonymousSession](../components/auth/AnonymousSession.tsx): `/login`을 뺀 모든 페이지에서 `ensureAnonymousSession()`을 부른다.
2. [lib/api.ts](../lib/api.ts)의 `request`: 매 요청 전에 `ensureAnonymousSession()`을 부르고, 401을 받으면 익명으로 다시 로그인한 뒤 한 번 더 시도한다.

## 1. 바뀌는 흐름

```text
세션 없음 ──▶ /welcome
               ├─ 익명으로 시작하기 ──▶ 익명 계정 생성 ──▶ next(기본 /)
               └─ Google 계정으로 계속 ──▶ Google 화면 ──▶ /auth/callback ──▶ next(기본 /)

익명 사용 중
  └─ 계정 메뉴 "Google로 기록 지키기" ──▶ Google 화면 ──▶ /auth/callback ──▶ 같은 사용자, 기록 유지
        └─ 그 Google 계정이 이미 가입되어 있으면 ──▶ /auth/callback ──▶ next?auth_error=… ──▶ 연결 실패 안내(Link-Conflict)
              ├─ "다른 Google 계정으로 연결" ──▶ 다시 기록 지키기
              └─ "기존 계정으로 로그인" ──▶ Google 화면 ──▶ 그 계정으로 전환
                    (지금 익명 기록은 옮겨지지 않고, 전환 뒤에는 다시 볼 수 없다)

Google 계정 ── 계정 메뉴 "로그아웃" ──▶ /welcome
```

- 익명 계정은 사용자가 "익명으로 시작하기"를 눌렀을 때만 만든다. 한 번 보고 나간 방문자나 봇 때문에 익명 사용자가 쌓이지 않는다.
- 세션이 남아 있으면(익명이든 Google이든) 다시 와도 바로 홈이 뜬다. 시작 화면은 세션이 없을 때만 보인다.
- Supabase 세션은 기본적으로 로그아웃하기 전까지 유지된다. 기간 제한(Time-box, Inactivity timeout)은 Pro 플랜 이상이라 "로그아웃 전까지 자동 로그인"으로 기획한다.

## 3. 경로별 접근 규칙(`proxy.ts`)

| 경로 | 세션 없음 | 익명 | Google 계정 |
| --- | --- | --- | --- |
| `/`, `/records` | → `/welcome?next=원래경로`(주소에 Supabase 오류 쿼리가 있으면 `error`로 옮겨 담는다) | 통과 | 통과 |
| `/welcome` | 통과 | → `/` | → `/` |
| `/auth/callback` | 통과 | 통과 | 통과 |
| ~~`/login`(개발 환경만)~~ | 지웠다(2026-10-26). 없는 주소라 404 | | |
| `/settings` | → `/welcome?next=/settings` | 통과 | 통과 |
| `/privacy`, `/terms` | 통과(하단 탭·헤더 메뉴 숨김) | 통과 | 통과 |
| `/api/*` | 리다이렉트하지 않음(Route Handler가 401) | | |

- `proxy.ts`에서 Supabase SSR 방식으로 서버 클라이언트를 만들고 `getClaims()`로 상태를 판단한다. 세션 쿠키 갱신도 여기서 한다(그동안 보류해 둔 `proxy.ts`).
- **리다이렉트할 때 쿠키를 옮겨 담는다.** `getClaims()`가 토큰을 갱신하며 응답에 넣은 쿠키가, 새로 만든 `NextResponse.redirect()`에는 없다. 그대로 돌려주면 갱신된 세션을 잃는다.
- **`next`는 안전한 값만 쓴다.** `/`로 시작하고 `//`로 시작하지 않는 상대 경로만 받고, 아니면 `/`로 바꾼다(오픈 리다이렉트 방지). `/welcome` → 익명 시작·Google 로그인(`/auth/callback?next=…`)까지 그대로 넘긴다.
- 운영 환경의 `/login`은 proxy가 막는다(`/_not-found`로 rewrite, 상태 404). 페이지의 `notFound()`만으로는 루트 `loading.tsx`가 응답을 200으로 먼저 보내서 상태 코드가 404가 되지 않는다(Next 16 문서 `not-found.md`, 2026-10-22 확인).
- Supabase가 콜백 대신 Site URL(`/`)로 오류를 보내는 경우가 있다(아래 [콜백 실패 처리](#콜백-실패-처리2026-10-21-확인)). 세션 없이 `/?error=…&error_code=…`로 오면, `/welcome`으로 보낼 때 `error_code`(없으면 `error`)를 `error`에 담아 안내가 뜨게 한다.
- matcher에서 정적 파일과 메타데이터 경로를 뺀다: `_next/static`, `_next/image`, `images/`, `favicon.ico`, `icon.png`, `apple-icon.png`, `opengraph-image`, `robots.txt`, `sitemap.xml`, `manifest`.
- 링크 미리보기(카톡·슬랙 등에 주소를 붙여넣었을 때 메신저 서버가 페이지를 읽어 만드는 카드)는 쿠키가 없어 `/`가 `/welcome`으로 리다이렉트된다. `/welcome`에도 홈과 같은 제목·설명·공유 이미지 메타데이터를 둔다(선택).
- Next 16 문서([16-proxy.md](../node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md))도 proxy를 리다이렉트 같은 가벼운 확인 용도로 설명한다. 실제 권한 확인은 지금처럼 Route Handler와 RLS가 맡는다.

### 콜백 실패 처리(2026-10-21 확인)

처음 계획은 실패하면 무조건 `/welcome?error=…`로 보내는 것이었다. 그러면 익명 사용자의 Google 연결이 실패했을 때 오류가 사라진다. 사용자는 여전히 익명 세션이라 proxy가 `/welcome`을 `/`로 돌려보내고, 그 과정에서 쿼리가 버려지기 때문이다. 그러면 연결 실패 안내(Link-Conflict)를 띄울 수 없다. 아래는 Supabase Auth(GoTrue) 소스와 설치된 `@supabase/auth-js` 2.117.3 코드로 확인한 동작이다.

#### Supabase가 실패를 돌려주는 방식

| 경우 | 돌아오는 곳 | 붙는 값 |
| --- | --- | --- |
| 이미 다른 사용자에게 연결된 Google 계정으로 `linkIdentity` | `redirectTo`(= `/auth/callback?next=…`) | `error_code=identity_already_exists`, `error`, `error_description`. 세션·code는 만들지 않는다 |
| 그 Google 이메일을 다른 계정이 이미 쓰는 경우(이메일 테스트 계정 등) | 같음 | `error_code=email_exists` |
| Google 화면에서 취소 | 같음 | `error=access_denied`. `error_code`는 없을 수 있다 |
| 흐름 정보를 읽기 전 실패(오래 방치해 상태 만료, `state` 손상 등) | **Site URL**(운영 주소의 `/`) | 같은 형식 |
| `redirectTo`가 Redirect URLs 허용 목록과 맞지 않을 때 | **Site URL**로 조용히 바뀐다(오류 없음) | 성공해도 `/?code=…`로 간다 |

- 오류를 붙일 때 **`redirectTo`에 있던 쿼리(`next`)는 그대로 둔다.** 오류 값은 쿼리와 `#` 뒤 양쪽에 붙는다. 서버 콜백은 쿼리만 읽으면 된다
- 실패하면 code를 주지 않으므로, 콜백이 `exchangeCodeForSession`을 부르지 않는 한 **세션은 그대로다**(사용자 ID 유지). 실패한 연결 뒤 다른 계정으로 바뀌었다는 사례도 있다(참고의 tortoise #1871). 시나리오 4에서 사용자 ID가 그대로인지 꼭 확인한다
- [Custom redirect after linkIdentity fails](https://github.com/orgs/supabase/discussions/32641)에 "실패하면 Site URL로 간다"는 글이 있다. 위 표의 마지막 두 경우(흐름 정보 전 실패, 허용 목록 불일치)에 해당한다

#### 결정: 콜백이 세션 유무로 돌아갈 곳을 고른다

- 세션이 없으면(시작 화면에서 Google 로그인 실패): `/welcome?error=<코드>&next=…`
- 세션이 있으면(익명 사용자의 연결·전환 실패): 하던 화면 `next`에 `?auth_error=<코드>`
- 코드는 `error_code`, 없으면 `error`를 쓴다. code 교환 실패는 그 오류의 `code`를 쓴다

`&link=1` 같은 표시를 콜백 주소에 붙이는 방법보다 이쪽을 골랐다. 이유는 다음과 같다.

- 표시가 없어도 세션 유무와 오류 코드만으로 구분된다. "Google로 기록 지키기"(`linkIdentity`)만 `identity_already_exists`·`email_exists`가 나고, 연결 실패 안내의 "기존 계정으로 로그인"(`signInWithOAuth`)은 연결이 아니라 이 오류가 나지 않는다
- 콜백 주소의 쿼리 가짓수가 줄어든다. 허용 목록은 쿼리까지 비교하기 때문이다(0단계)

| `auth_error` | 화면(홈·기록) |
| --- | --- |
| `identity_already_exists`, `email_exists` | 연결 실패 안내(보드: 기록 지키기 실패 · 이미 가입된 구글 계정) |
| `access_denied`(취소) | 아무것도 띄우지 않는다 |
| 그 밖 | 짧은 안내 "Google 연결을 마치지 못했어요. 잠시 후 다시 시도해 주세요."(보드 없음. 시작 화면의 분홍 안내와 같은 모양) |

안내를 띄운 뒤에는 `router.replace`로 주소에서 `auth_error`를 지운다. 새로고침해도 다시 뜨지 않게 하기 위해서다.

- [x] `app/auth/callback/route.ts`: `code`를 세션으로 바꾸고 `next`로 보낸다. 실패하면 세션 유무에 따라 `/welcome?error=…` 또는 `next?auth_error=…`([콜백 실패 처리](#콜백-실패-처리2026-10-21-확인))

```ts
// app/auth/callback/route.ts
import { NextResponse } from "next/server";
import { createClient } from "@/lib/supabase/server";

// Google 로그인·연결(linkIdentity)이 돌아오는 곳. 성공하면 code를 세션으로 바꿔 next로 보낸다.
// 실패하면 Supabase가 redirectTo의 쿼리(next)를 그대로 두고 error·error_code를 붙여 보낸다(code 없음).
export async function GET(request: Request) {
  const { searchParams, origin } = new URL(request.url);
  const code = searchParams.get("code");
  const nextParam = searchParams.get("next") ?? "/";
  const next = nextParam.startsWith("/") && !nextParam.startsWith("//") ? nextParam : "/";
  const supabase = await createClient();

  let reason = searchParams.get("error_code") ?? searchParams.get("error");
  if (code && !reason) {
    const { error } = await supabase.auth.exchangeCodeForSession(code);
    if (!error) return NextResponse.redirect(new URL(next, origin));
    reason = error.code ?? "auth_failed";
  }
  reason ??= "auth_failed";

  // 세션이 남아 있으면(익명 사용자의 연결·전환 실패) 하던 화면으로 돌아가 안내한다.
  // /welcome으로 보내면 proxy가 세션 있는 사용자를 /로 돌려보내며 오류가 사라진다.
  const { data } = await supabase.auth.getClaims();
  const url = new URL(data ? next : "/welcome", origin);
  if (data) {
    url.searchParams.set("auth_error", reason);
  } else {
    url.searchParams.set("error", reason);
    url.searchParams.set("next", next);
  }
  return NextResponse.redirect(url);
}
```

- 쿠키: Route Handler에서 `cookies()`로 쓴 세션 쿠키는 돌려주는 `NextResponse.redirect`에도 실린다. Supabase 공식 Next.js 예제와 같은 방식이다
- (2026-10-22 변경) 돌아갈 주소는 `request.url`이 아니라 요청 헤더(`x-forwarded-host`, 없으면 `host`)로 만든다. Supabase 공식 예제와 같은 방식이다. Route Handler의 `request.url`·`nextUrl`은 dev 서버가 뜬 호스트(`localhost`)라서, 다른 주소(휴대폰에서 `192.168.x.x:3000` 등)로 열어도 `localhost`로 보내 버렸다. 위 코드 블록은 처음 계획 그대로이고, 실제 코드는 [route.ts](../app/auth/callback/route.ts)의 `requestOrigin`이다. 배포 확인(5단계)에서 리디렉션 호스트를 본다
- 휴대폰에서 LAN 주소로 Google 로그인까지 하려면 Supabase Redirect URLs에 그 주소(`http://192.168.x.x:3000/**`)도 넣어야 한다

- [x] `lib/api.ts`에 Google 로그인 함수. `prompt: "select_account"`로 로그아웃 뒤에도 계정을 고를 수 있게 한다. 바로 실패하면(Google 제공자 꺼짐 등) 오류를 던져 화면에서 안내한다

#### 계정 삭제와 Google 연결 해제(검토 중)

Google 계정 자체는 지울 수 없다. 끊을 수 있는 것은 Google 계정 설정의 '서드파티 앱 및 서비스' 목록에 있는 이 앱과의 연결이다. 연결을 끊으려면 Google 토큰 취소 주소(`https://oauth2.googleapis.com/revoke`)에 그 사용자의 Google 토큰을 보내야 한다.

- **지금 바로 안 되는 이유:** Supabase는 Google 로그인 직후 세션에 Google 토큰(`session.provider_token`)을 한 번만 넣어 주고 저장·갱신하지 않는다(auth-js 2.117.3 `Session` 타입에서 확인). 토큰은 1시간이면 만료되어, 며칠 뒤 삭제할 때는 보낼 토큰이 없다
- **어느 방법이든 Supabase 사용자 삭제는 같다:** `delete_my_account()`의 `delete from auth.users where id = auth.uid()`. 익명·개발용 이메일 계정은 Google 단계 없이 이것만 한다
- **기본안(연결 해제를 하지 않을 때):** 삭제 확인이나 완료 화면에 "Google 계정 설정에서 이 앱과의 연결도 끊을 수 있어요" 링크(`https://myaccount.google.com/connections`). 처리방침 6절에 한 줄. 기본 범위(이메일·이름·사진)만 받고 Google 토큰을 저장하지 않아, 연결이 남아도 앱이 Google 데이터를 계속 볼 수 없다

**방법 A: Supabase로 Google 로그인을 한 번 더 한다**

```text
계정 삭제 확인 → signInWithOAuth(google, login_hint=이메일) → Google 화면 → /auth/callback(삭제용 표시)
  → exchangeCodeForSession 결과의 session.provider_token으로 revoke → delete_my_account → /welcome
```

- 장점: 이미 쓰는 Supabase 리디렉션 로그인 그대로다. 새 스크립트·환경변수·Google Cloud 설정이 없다. 지우기 전에 본인을 다시 확인하는 효과가 있다
- 위험: Google 화면에서 **다른 계정**을 고르면 코드를 교환하는 순간 세션이 그 계정으로 바뀐다. 그 Google 계정이 처음이면 Supabase가 콜백 단계에서 **새 사용자를 만든다**. 확인 없이 진행하면 엉뚱한 계정을 지울 수 있다
- 막으려면: 원래 세션 쿠키를 덮어쓰지 않는 별도 클라이언트(쿠키 쓰기를 하지 않는 서버 클라이언트)로 코드를 교환해 사용자 ID를 원래 세션과 비교한다. 다르면 지우지 않고, 새로 생긴 세션을 로그아웃하고 안내한다. 잘못 생긴 사용자는 남을 수 있다
- 콜백에 삭제 흐름 분기, 실패 안내(취소, 다른 계정, revoke 실패)가 늘어난다

**방법 B: Google 토큰만 따로 받는다(Google Identity Services 토큰 팝업)**

```text
계정 삭제 확인 → Google 팝업(google.accounts.oauth2.initTokenClient, hint=이메일, scope=openid email)
  → 브라우저가 받은 Google 토큰을 POST /api/account/delete 로 보냄
  → 서버: 1) getUser()로 Google identity 확인(UserIdentity.id = Google 사용자 ID)
          2) Google tokeninfo로 토큰 주인의 sub 확인 → 다르면 400(다른 계정을 골랐어요)
          3) revoke로 연결 해제
          4) rpc('delete_my_account')
          5) 204
  → 브라우저 signOut({ scope: "local" }) → /welcome
```

- 장점: Supabase 세션을 건드리지 않아 다른 계정을 골라도 세션이 바뀌거나 사용자가 새로 생기지 않는다. 새 콜백 경로가 없고 확인 로직이 삭제 API 한 곳에 모인다. 토큰은 한 번 쓰고 버려 저장하지 않는다
- 준비: Google Cloud OAuth 클라이언트의 '승인된 자바스크립트 원본'에 `http://localhost:3000`과 배포 주소(0단계의 "비운다" 결정이 바뀐다). 환경변수 `NEXT_PUBLIC_GOOGLE_CLIENT_ID`(Supabase에 넣은 클라이언트 ID와 같은 공개 값, 시크릿 불필요). 스크립트 `https://accounts.google.com/gsi/client`는 설정 페이지에서만 불러온다
- 감안할 것: 확인 대화상자 뒤에 Google 팝업이 한 번 더 뜬다(보드에 없는 단계라 "Google 계정 확인 창이 열려요" 같은 안내 필요). 팝업은 버튼 클릭 안에서 열어야 막히지 않는다. 서버가 Google에 바깥 요청 두 번(tokeninfo, revoke)을 한다

**두 방법 공통**

- 순서는 연결 해제 → 계정 삭제. revoke가 실패해도 삭제는 계속하고, 완료 뒤 기본안의 링크를 보여준다. 팝업을 닫거나 Google 화면에서 취소하면 삭제하지 않고 대화상자 안에 안내한다
- 연결을 끊으면 같은 Google 계정으로 다시 가입할 때 동의 화면이 처음처럼 다시 뜬다
- 로그인할 때 Google 갱신 토큰을 받아 DB에 저장해 두는 방법(방법 C)은 쓰지 않는다. Google 토큰을 보관해야 해서 처리방침에 적을 민감 정보가 생기고, 로그인할 때마다 동의 화면이 뜰 수 있다

## 5. 확인할 시나리오

1. 쿠키가 없을 때 `/`나 `/records`에 들어가면 `/welcome`으로 가고, 익명 시작·Google 로그인 뒤 원래 경로로 돌아오는지
2. 익명으로 시작한 뒤 새로고침하거나 다시 방문하면 바로 홈이 뜨는지
3. 익명으로 기록을 쌓은 뒤 "Google로 기록 지키기"를 하면 기록이 그대로인지(사용자 ID 유지)
4. 3번에서 이미 가입된 Google 계정을 고르면 하던 화면(`/records`에서 했다면 `/records`)으로 돌아와 연결 실패 안내가 뜨는지
   - 익명 기록과 세션이 그대로인지 본다. **사용자 ID가 바뀌지 않았는지**도 본다(실패한 연결 뒤 다른 계정으로 바뀐 사례가 있다)
   - 콜백이 받은 `error_code`가 `identity_already_exists`인지 본다
   - 안내의 "다른 Google 계정으로 연결"에서 계정 선택 화면이 다시 뜨는지 본다
5. 4번의 연결 실패 안내에서 "기존 계정으로 로그인"을 누르면 그 계정의 기록이 보이는지. (2026-10-26 변경) 익명 기록이 0개면 안내 없이 바로 그 계정으로 로그인되는지(Google 계정이 하나·여럿 로그인된 경우 각각). 익명 계정 메뉴에 "기존 Google 계정으로 로그인"이 없는지

   - 세션이 없으면 `/welcome?error=access_denied`(분홍 안내)
   - 익명 상태의 연결·전환 취소면 하던 화면으로 돌아오고, 안내는 뜨지 않는다. 새로고침해도 주소에 `auth_error`가 남지 않아야 한다
7. Google 계정으로 로그아웃하면 `/welcome`으로 가고, 다시 로그인하면 계정 기록이 보이는지. 다른 브라우저·기기에서 로그인해도 같은 기록인지
8. 지운 사용자의 쿠키가 남아 있을 때 API 401 → 쿠키 삭제 → `/welcome`으로 가고 무한 리다이렉트가 없는지
9. 각 상태에서 `/welcome`, `/auth/callback`, `/settings`, `/privacy`·`/terms`에 들어갔을 때 3번 표대로 되는지(`/login`은 지워 404)
10. `next`에 외부 주소(`//example.com`, `https://…`)를 넣으면 `/`로 가는지
11. ~~`/login` 개발 환경 전용 확인~~(2026-10-26에 `/login`을 지워 해당 없음)
12. 배포 주소에서 1~3번과 `/login` 404
13. 로컬(`pnpm dev`)에서 Google 로그인을 마치면 운영 주소가 아니라 `localhost:3000`으로 돌아오는지(Redirect URLs 와일드카드)

    - Supabase 대시보드에서 그 사용자와 `daily_entries` 기록이 지워졌는지
    - 같은 Google 계정으로 다시 로그인하면 빈 새 계정(기록 0개)으로 시작하는지

## 6. 남은 결정과 구현할 때 확인할 것

- (소스로 확인, 실제 동작은 시나리오 4에서 확인) **연결 실패 오류 형태.** `redirectTo`의 쿼리를 그대로 두고 `error_code=identity_already_exists`(또는 `email_exists`)를 붙여 돌아온다([콜백 실패 처리](#콜백-실패-처리2026-10-21-확인))
- (결정, 2026-10-21) **익명 계정 메뉴는 "Google로 기록 지키기" 하나.** "기존 Google 계정으로 로그인" 메뉴를 두면, 처음 쓰는 Google 계정을 골랐을 때 빈 새 계정이 생기고 익명 기록은 쓸 일 없이 남는다. 그래서 메뉴를 없앴다. 이미 가입된 계정일 때만 연결 실패 안내에서 "기존 계정으로 로그인"을 고른다
- **연결 뒤 프로필 정보.** 익명 계정에 Google을 붙인 뒤 `user.email`, 이름, 사진이 어디에 채워지는지(2. 화면)
- (결정, 2026-10-21) **Google 버튼 모양.** 공식 생성기 코드, 텍스트 모드, "Google 계정으로 계속"([2. 화면](#2-화면)). 텍스트 모드 코드는 받아서 계획서에 넣어 두었다
- **남는 익명 계정 정리.** 연결 실패 안내에서 "기존 계정으로 로그인"을 하면 그 익명 계정은 다시 들어갈 방법이 없지만 DB에는 남는다. 자동 정리는 없으므로 나중에 오래된 익명 사용자를 지우는 SQL(예: 30일 이상)을 둔다

## 7. 이번 범위에서 빼는 것

- **익명 기록을 이미 있는 계정으로 합치기:** 하루 기록이 1개라 같은 날짜끼리 겹치므로 규칙과 서버 함수가 따로 필요하다. 이번에는 확인 대화상자와 연결 실패 안내만 둔다
- **익명 가입 남용 방지(CAPTCHA):** 버튼을 눌러야 익명 계정이 생기고, Supabase의 IP당 시간당 30회 제한이 있다
- (6단계로 옮김, 2026-10-22) **개인정보 처리 안내:** Google 프로덕션 게시에 개인정보처리방침 URL이 필수라서, 1~5단계에서는 빼고 [6단계: 공개 준비](#6단계-공개-준비프로덕션-게시-전)에서 만든다
- (범위에 넣음, 2026-10-22) **계정 삭제:** [4C단계](#4c단계-계정-삭제보드-29)로 옮겼다
- **익명 사용자의 "기록 모두 지우기":** 익명 사용자에게는 계정 삭제를 두지 않는다. 브라우저 데이터를 지우면 다시 들어갈 수 없어서 어차피 오래된 익명 계정 정리 SQL로 지워지기 때문이다. 필요해지면 다시 본다
- **카카오 로그인:** Supabase가 지원한다. 이메일을 받으려면 카카오 비즈 앱 전환이 필요하지만, 이메일 없이 닉네임만 받고 Supabase에서 "Allow users without an email"을 켜면 비즈 앱 없이도 된다
- **이메일 가입, 메일 인증, 비밀번호 찾기:** 하지 않는다(위 '이메일 가입을 하지 않는 이유')
