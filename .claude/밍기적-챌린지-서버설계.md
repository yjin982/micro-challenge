# 밍기적 챌린지 서버 설계

> 원본: Claude 아티팩트 (2026-10-15에 마크다운으로 내보냄)

2026-09-29 · @유진

'밍기적 챌린지 기획서'의 규칙을 코드로 옮기기 위한 백엔드 초안이다. Next.js Route Handler가 요청을 받고, 뽑기·재뽑기·완료는 Supabase(Postgres) 함수 하나씩이 처리한다. 미션 제출·관리자 기능은 4단계(보류)라 따로 모았고, 만들지 않을 수도 있다.

## 서버 API 명세

핵심 API는 5개다. 상태를 바꾸는 요청은 전부 Postgres 함수(RPC) 하나로 끝나고, Route Handler는 세션 확인, 입력 검사, 에러 변환만 맡는다. 미션 제출·관리자 API 6개는 4단계(보류) 표에 따로 모았다.

### 공통 규칙

- 방식: Next.js App Router의 Route Handler(`app/api/.../route.ts`). curl로 바로 시험할 수 있어서 Server Action 대신 고른다.
- 사용자 식별: `@supabase/ssr`의 세션 쿠키. 클라이언트는 앱을 처음 열 때 `signInAnonymously()`를 부르고, 이후 모든 요청에 쿠키가 붙는다.
- 쓰기: Route Handler가 사용자 세션으로 `supabase.rpc()`를 부른다. 함수 안에서 `auth.uid()`로 본인을 확인하므로 서비스 키(service role)는 쓰지 않는다.
- 날짜: 서버(DB)의 `kst_day(now())`만 믿는다. 도착 시각에서 1분을 뺀 뒤 한국 날짜로 바꾼 값이다.
- 날짜 확인: 뽑기·재뽑기·완료는 화면이 알고 있는 날짜를 `date`로 보낸다. 서버 날짜와 다르면 `DAY_CHANGED`를 돌려주고, 화면은 오늘 상태를 다시 불러온다. 화면은 날짜를 직접 계산하지 않고 GET /api/today가 돌려준 date를 그대로 쓴다. 그래야 00:00대(1분 유예)에도 화면과 서버의 날짜가 엇갈리지 않는다. 화면을 켜둔 채 자정이 지났는지는 화면에 돌아올 때 GET /api/today를 다시 불러 확인한다.
- 응답: 성공은 JSON 본문, 실패는 `{ "error": { "code": "NO_REROLLS", "message": "..." } }`와 HTTP 상태 코드.

### 엔드포인트

| 메서드 | 경로 | 하는 일 | 호출 함수 | 쓰는 화면 |
|---|---|---|---|---|
| GET | `/api/today` | 오늘 상태, 연속·누적 수, 최근 기록 3개 | `get_today` | 홈 전체 |
| POST | `/api/today/draw` | 첫 카드 뽑기(재뽑기 횟수에 안 들어감) | `draw_first` | 홈 뽑기 전 |
| POST | `/api/today/reroll` | 재뽑기 | `reroll_today` | 홈 도전중 |
| POST | `/api/today/complete` | 완료, 도장 결정 | `complete_today` | 홈 도전중 → 완료 연출 |
| GET | `/api/records?month=2026-09` | 한 달치 완료 기록 | `get_month` | 기록, 연속 달성 |

**4단계(보류): 미션 제출·관리자 API.** 관리자 역할을 정한 뒤에 만들고, 만들지 않을 수도 있다.

| 메서드 | 경로 | 하는 일 | 호출 함수 | 쓰는 화면 |
|---|---|---|---|---|
| GET | `/api/submissions` | 내 제출 목록과 오늘 제출 수 | submissions 테이블 직접 조회 | 설정 |
| POST | `/api/submissions` | 미션 제출 | `submit_mission` | 설정 |
| GET | `/api/admin/submissions?status=pending` | 제출 목록과 상태별 개수 | `admin_list_submissions` | 관리자 |
| POST | `/api/admin/submissions/[id]/approve` | 승인(문구·난이도 수정 가능) | `admin_approve` | 관리자 |
| POST | `/api/admin/submissions/[id]/reject` | 반려 | `admin_reject` | 관리자 |
| POST | `/api/admin/logout` | 관리자 로그아웃 | `supabase.auth.signOut` | 관리자 |

4단계의 관리자 로그인은 API를 따로 두지 않고 `/admin/login` 화면에서 `signInWithPassword()`를 바로 부른다.

우선순위: 핵심 API 5개와 missions·daily_entries 테이블만으로 1~3단계가 완결된다. 4단계 API에 필요한 함수·테이블은 맨 아래 '부록: 4단계(보류) SQL'에 모았다.

### 요청과 응답

GET /api/today는 홈이 그리는 데 필요한 것을 한 번에 돌려준다. `state`가 화면을 고른다: `not_drawn` → 뽑기 전, `challenge` → 도전중, `done` → 연속 달성.

```json
{
  "date": "2026-09-28",
  "state": "challenge",
  "mission": { "id": "E021", "text": "물 마실 때 이상한 포즈로 마시기", "difficulty": "easy" },
  "rerollsLeft": 2,
  "completedAt": null,
  "stampId": null,
  "streak": 4,
  "totalCompleted": 17,
  "recent": [
    { "date": "2026-09-27", "missionText": "영화 주인공처럼 걸어보기", "stampId": "p06" }
  ]
}
```

- `streak`: 오늘 완료했으면 오늘까지, 아직이면 어제까지 이어진 날 수.
- `recent`: 완료한 날만 최신순 최대 3개. 빈 배열이면 화면은 최근 기록 영역을 숨긴다.
- draw·reroll: 요청 `{ "date": "2026-09-28" }` → 응답은 위와 같은 오늘 상태.
- complete: 요청 `{ "date": "2026-09-28" }` → 오늘 상태(`state: "done"`, `stampId`, `completedAt` 채워짐).
- records: 응답 `{ "month": "2026-09", "firstMonth": "2026-08", "days": [{ "date", "missionText", "stampId", "completedAt" }] }`. `firstMonth`는 처음 쓴 달로, 이전 달 화살표를 막는 데 쓴다.
- (4단계) submissions POST: 요청 `{ "text": "양말 짝짝이로 신어보기", "difficulty": "easy" }` → 응답 `{ "id", "status": "pending", "todayCount": 1 }`.
- (4단계) approve: 요청 `{ "text"?, "difficulty"? }`(고친 값만) → 응답 `{ "missionId": "S0001" }`.

### 에러 코드

| 코드 | HTTP | 언제 | 화면 처리 |
|---|---|---|---|
| UNAUTHENTICATED | 401 | 세션 없음 | 익명 로그인 후 한 번 재시도 |
| DAY_CHANGED | 409 | 화면의 날짜와 서버 날짜가 다름 | 오늘 상태 다시 불러오기 |
| ALREADY_DRAWN | 409 | 이미 첫 카드를 뽑음(다른 탭 등) | 오늘 상태 다시 불러오기 |
| NOT_DRAWN | 409 | 뽑기 전에 재뽑기·완료 요청 | 오늘 상태 다시 불러오기 |
| NO_REROLLS | 409 | 재뽑기 3회를 다 씀 | 다시 뽑기 막기 |
| ALREADY_COMPLETED | 409 | 이미 완료한 날의 재뽑기·완료 | 연속 달성 화면으로 |
| FORBIDDEN | 403 | (4단계) 관리자가 아닌 사람의 /api/admin 요청 | 관리자 로그인 화면 |
| INVALID_INPUT | 400 | (4단계) 제출 문구 5~40자 밖, 난이도 값 오류 | 입력란 아래 안내 |
| DAILY_LIMIT | 429 | (4단계) 오늘 제출 3개를 넘김 | "오늘은 3개까지예요" |
| DUPLICATE | 409 | (4단계) 같은 문구를 이미 냈거나 같은 미션이 있음 | "이미 있는 미션이에요" |
| NOT_FOUND | 404 | (4단계) 없는 제출 ID, 이미 처리된 제출 | 목록 새로고침 |

DB 함수는 이 코드를 예외 메시지로 던지고(`raise exception 'NO_REROLLS'`), Route Handler가 코드를 HTTP 상태로 바꾼다.

### Route Handler 예시

```ts
// app/api/today/reroll/route.ts
import { NextResponse } from 'next/server';
import { createClient } from '@/lib/supabase/server';
import { toErrorResponse } from '@/lib/api-error';

export async function POST(req: Request) {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return toErrorResponse('UNAUTHENTICATED');

  const { date } = await req.json();
  const { data, error } = await supabase.rpc('reroll_today', { p_date: date });
  if (error) return toErrorResponse(error.message); // 'NO_REROLLS' → 409
  return NextResponse.json(data);
}
```

## 테이블 SQL 초안

Supabase SQL Editor에서 1번부터 7번까지 순서대로 실행하면 핵심 기능(1~3단계)이 준비된다. 테이블은 missions, daily_entries 2개이고, 쓰기 정책은 두지 않아 모든 쓰기는 `security definer` 함수가 맡는다. 미션 제출·관리자용 SQL은 맨 아래 '부록: 4단계(보류) SQL'에 따로 모았고, 4단계를 만들지 않으면 실행하지 않는다.

### 1. 날짜 도우미 함수

```sql
-- 도착 시각 - 1분을 한국 날짜로 (00:00:59 도착까지는 전날)
create or replace function public.kst_day(ts timestamptz default now())
returns date language sql stable as $$
  select ((ts - interval '1 minute') at time zone 'Asia/Seoul')::date
$$;
```

### 2. 테이블

```sql
create table public.missions (
  id          text primary key,                 -- E001~E180, C01~C20 (4단계를 만들면 S0001~)
  text        text not null check (btrim(text) <> ''),     -- 길이 제한 없음(빈 문구만 막음)
  difficulty  text not null check (difficulty in ('easy', 'challenge')),
  category    text,                             -- 내부 분류 (4단계 제출분은 null)
  source      text not null default 'seed' check (source in ('seed', 'user')),
  is_active   boolean not null default true,
  created_at  timestamptz not null default now()
);

create table public.daily_entries (
  user_id            uuid not null references auth.users (id) on delete cascade,
  date               date not null,             -- kst_day() 기준
  current_mission_id text not null references public.missions (id),
  seen_mission_ids   text[] not null default '{}',
  reroll_count       int not null default 0 check (reroll_count between 0 and 3),
  completed_at       timestamptz,
  stamp_id           text check (stamp_id in ('p01','p02','p03','p04','p05','p06')),
  created_at         timestamptz not null default now(),
  primary key (user_id, date),
  check ((completed_at is null) = (stamp_id is null))
);
create index daily_entries_done_idx
  on public.daily_entries (user_id, date desc) where completed_at is not null;
```

### 3. 접근 규칙(RLS)

```sql
alter table public.missions      enable row level security;
alter table public.daily_entries enable row level security;

create policy "missions: 사용 중인 미션 읽기" on public.missions
  for select to anon, authenticated using (is_active);

create policy "daily_entries: 본인 행 읽기" on public.daily_entries
  for select to authenticated using (user_id = (select auth.uid()));

-- insert/update/delete 정책은 만들지 않는다 → 아래 함수로만 쓴다.
-- missions의 추가·비활성화는 운영자가 대시보드(Table Editor, SQL Editor)에서 직접 한다.
```

익명 로그인 사용자도 DB에서는 `authenticated` 역할이라 위 정책이 그대로 적용된다.

### 4. 내부 도우미(뽑기 규칙, 오늘 상태)

```sql
-- ============================================================
-- [공통 서식 읽는 법]
--  create or replace function 이름(인자 타입, ...)  : 함수를 만들거나 덮어쓴다
--  returns 타입       : 돌려주는 값의 타입 (boolean, text, jsonb ...)
--  language sql      : 본문이 SELECT 한 문장뿐인 간단한 함수
--  language plpgsql  : 변수, if, 여러 문장을 쓸 수 있는 함수 (JS 함수와 비슷)
--  stable / volatile : stable = 읽기만 함, volatile = random()처럼 매번 결과가 다를 수 있음
--  security definer  : 호출한 사람이 아니라 '함수를 만든 관리자' 권한으로 실행된다.
--                      RLS 때문에 사용자가 직접 못 보는 표도 읽을 수 있으므로,
--                      함수 안에서 반드시 '누구 것만 볼지'를 직접 걸러야 한다.
--  set search_path = public : 표 이름을 public 스키마에서만 찾는다 (보안용 관례)
--  $$ ... $$         : 함수 본문을 감싸는 따옴표. 안에서 ' 를 그대로 쓸 수 있다
--  auth.uid()        : 지금 로그인한 사용자의 id (익명 포함). 로그인 안 했으면 null
-- ============================================================


-- ------------------------------------------------------------
-- pick_mission(사용자, 오늘 날짜, 오늘 이미 본 미션 목록): 뽑기 규칙
--   돌려주는 값: 뽑힌 미션 id 하나 (예: 'E021')
--
--   1차 후보 = 사용 중인 미션 전체
--                  - 최근 180일 안에 완료한 미션   (done)
--                  - 최근 14일 안에 넘긴 미션    (skipped)
--                  - 오늘 이미 본 미션          (p_seen)
--                  → 이 중 하나를 무작위로
--   2차(1차 후보가 하나도 없을 때) = 오늘 본 것만 빼고,
--                  마지막으로 본 날이 가장 오래된 미션부터
--
--   · 180일/14일은 무언가를 꺼 두는 게 아니라 뽑을 때마다 daily_entries를 보고 계산한다.
--     그래서 기간이 지나면 따로 복구하지 않아도 다시 후보가 된다.
--   · 내부용: SQL 6번에서 사용자가 직접 부르지 못하게 막는다
-- ------------------------------------------------------------
create or replace function public.pick_mission(p_user uuid, p_day date, p_seen text[])
returns text language plpgsql volatile security definer set search_path = public as $$
declare v_id text;   -- 결과를 담을 변수 (JS의 let v_id)
begin
  -- with A as (...), B as (...) : 아래 select에서 쓸 임시 표(이름 붙인 하위 쿼리)
  with done as (
    -- 내가 최근 180일 안에 완료한 미션 id들
    select current_mission_id as id from daily_entries
    where user_id = p_user and completed_at is not null and date > p_day - 180
  ), skipped as (
    -- 내가 최근 14일(오늘 제외) 동안 본 미션 중 그날 완료하지 않은 것 = 넘긴 미션
    -- unnest(배열): seen_mission_ids 배열을 한 줄에 하나씩 펼친다
    select s.id from daily_entries e, unnest(e.seen_mission_ids) as s(id)
    where e.user_id = p_user and e.date > p_day - 14 and e.date < p_day
      -- 그날 완료한 미션은 '넘긴 것'이 아니므로 뺀다
      and s.id is distinct from (case when e.completed_at is not null then e.current_mission_id end)
  )
  select m.id into v_id from missions m          -- into v_id: 결과를 변수에 담는다
  where m.is_active                              -- 운영자가 끈 미션 제외
    and m.id <> all (p_seen)                     -- 오늘 본 미션 제외 (배열의 어느 값과도 다름)
    and m.id not in (select id from done)        -- 180일 내 완료 제외
    and m.id not in (select id from skipped)     -- 14일 내 넘긴 것 제외
  order by random() limit 1;                     -- 무작위로 섞어 하나만

  -- 1차 후보가 없으면(v_id가 비어 있으면) 2차 규칙
  if v_id is null then
    select m.id into v_id from missions m
    -- left join lateral: 미션마다 '내가 마지막으로 본 날'을 구해 붙인다 (못 본 미션은 null)
    left join lateral (
      select max(e.date) as last_seen from daily_entries e
      where e.user_id = p_user and m.id = any (e.seen_mission_ids)
    ) l on true
    where m.is_active and m.id <> all (p_seen)
    order by l.last_seen asc nulls first,        -- 한 번도 안 본 것 → 오래전에 본 것 순
             random() limit 1;                   -- 같은 날이면 무작위
  end if;
  return v_id;
end $$;


-- ------------------------------------------------------------
-- today_state(사용자, 오늘 날짜): GET /api/today 응답 JSON을 만든다
--   돌려주는 값 예: { "date", "state", "mission", "rerollsLeft", "completedAt",
--                    "stampId", "streak", "totalCompleted", "recent" }
--   · 뽑기·재뽑기·완료 함수도 끝난 뒤 이 함수를 불러 같은 모양으로 응답한다
--   · 내부용: 사용자는 get_today()를 통해서만 부른다
-- ------------------------------------------------------------
create or replace function public.today_state(p_user uuid, p_day date)
returns jsonb language sql stable security definer set search_path = public as $$
  with e as (
    -- 오늘 행 (없으면 아직 뽑기 전)
    select * from daily_entries where user_id = p_user and date = p_day
  ),
  done as (
    -- 내가 완료한 날짜 전부
    select date from daily_entries where user_id = p_user and completed_at is not null
  ),
  start as (
    -- 연속 계산 시작점: 오늘 완료했으면 오늘, 아니면 어제
    select case when exists (select 1 from done where date = p_day)
                then p_day else p_day - 1 end as d
  ),
  g as (
    -- 연속된 날 묶기: 날짜에서 순번(1,2,3...)을 빼면 연속된 날들은 같은 값(grp)이 된다
    --   예) 9/25,26,27 → 순번 1,2,3 → 9/24,9/24,9/24 (같은 묶음)
    --       9/29 → 순번 4 → 9/25 (다른 묶음, 하루가 비었기 때문)
    select date, date - (row_number() over (order by date))::int as grp from done
  )
  select jsonb_build_object(                     -- jsonb_build_object('키', 값, ...): JSON 객체 만들기
    'date', p_day,
    'state', case when not exists (select 1 from e) then 'not_drawn'      -- 오늘 행 없음
                  when (select completed_at from e) is null then 'challenge'  -- 뽑았지만 미완료
                  else 'done' end,                                         -- 완료
    'mission', (select jsonb_build_object('id', m.id, 'text', m.text, 'difficulty', m.difficulty)
                from e join missions m on m.id = e.current_mission_id),   -- 뽑기 전이면 null
    'rerollsLeft', coalesce(3 - (select reroll_count from e), 3),          -- coalesce(a, b): a가 null이면 b
    'completedAt', (select completed_at from e),
    'stampId', (select stamp_id from e),
    -- 시작점(오늘 또는 어제)이 속한 묶음의 날 수 = 연속 일수. 시작점이 완료 날이 아니면 0
    'streak', (select count(*) from g
               where grp = (select g2.grp from g g2, start where g2.date = start.d)),
    'totalCompleted', (select count(*) from done),
    -- 최근 완료 3개 (최신순). 하나도 없으면 빈 배열 []
    'recent', coalesce((select jsonb_agg(r order by r.date desc) from (
        select e2.date, m.text as "missionText", e2.stamp_id as "stampId"
        from daily_entries e2 join missions m on m.id = e2.current_mission_id
        where e2.user_id = p_user and e2.completed_at is not null
        order by e2.date desc limit 3) r), '[]'::jsonb)
  )
$$;
```

`streak`는 완료한 날짜에서 순번을 뺀 값이 같은 묶음(연속된 날들)을 찾고, 오늘(완료 전이면 어제)이 속한 묶음의 크기를 센다. 어제도 완료하지 않았으면 0이다.

### 5. API가 부르는 함수

```sql
-- ============================================================
-- [이 블록에서 새로 나오는 서식]
--  declare 변수 타입 := 값;   : 함수 안에서 쓸 변수 선언 (JS의 let)
--  raise exception '코드'    : 에러를 던지고 즉시 멈춘다 (JS의 throw).
--                              이 함수에서 바꾼 내용은 모두 취소된다.
--                              Route Handler는 error.message로 코드를 받아 HTTP 상태로 바꾼다
--  is distinct from          : '다르다'(<>)와 같되 null도 제대로 비교한다
--  select * into e ... for update
--                            : 행을 읽어 변수 e에 담고, 이 함수가 끝날 때까지 잠근다.
--                              같은 행을 동시에 건드리는 다른 요청(다른 탭)은 줄을 서서 기다린다
--  if not found then         : 바로 앞의 select/update가 행을 못 찾았으면
--  exception when ... then   : 함수 안에서 특정 DB 에러가 나면 잡아서 처리 (JS의 catch)
--
-- [각 함수의 공통 순서]
--  1) 로그인 확인  2) 날짜 확인  3) 규칙 검사  4) 쓰기  5) today_state()로 응답
-- ============================================================


-- ------------------------------------------------------------
-- get_today()  ← GET /api/today
--   오늘 상태를 돌려준다. 읽기만 하고 아무것도 바꾸지 않는다
-- ------------------------------------------------------------
create or replace function public.get_today()
returns jsonb language plpgsql stable security definer set search_path = public as $$
begin
  if auth.uid() is null then raise exception 'UNAUTHENTICATED'; end if;  -- 세션 없으면 거절
  return today_state(auth.uid(), kst_day());   -- kst_day(): 자정 1분 유예를 반영한 '오늘'
end $$;


-- ------------------------------------------------------------
-- draw_first(화면이 아는 날짜)  ← POST /api/today/draw
--   그날 첫 카드를 뽑는다. 재뽑기 횟수에는 들어가지 않는다.
--   오늘 행(daily_entries)을 이 함수가 처음 만든다
-- ------------------------------------------------------------
create or replace function public.draw_first(p_date date)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_uid uuid := auth.uid(); v_day date := kst_day(); v_id text;
begin
  if v_uid is null then raise exception 'UNAUTHENTICATED'; end if;
  -- 화면을 켜둔 채 자정이 지났으면 화면의 날짜와 서버 날짜가 다르다 → 다시 불러오게 한다
  if p_date is distinct from v_day then raise exception 'DAY_CHANGED'; end if;
  v_id := pick_mission(v_uid, v_day, '{}');     -- '{}' = 빈 배열(오늘 본 미션 없음)
  insert into daily_entries (user_id, date, current_mission_id, seen_mission_ids)
  values (v_uid, v_day, v_id, array[v_id]);    -- 본 목록에 첫 카드를 넣어 둔다
  return today_state(v_uid, v_day);
exception when unique_violation then
  -- (user_id, date)가 이미 있음 = 다른 탭에서 먼저 뽑았다. 기본키 덕분에 두 번 들어갈 수 없다
  raise exception 'ALREADY_DRAWN';
end $$;


-- ------------------------------------------------------------
-- reroll_today(화면이 아는 날짜)  ← POST /api/today/reroll
--   오늘 카드를 다른 미션으로 바꾼다. 하루 최대 3번
-- ------------------------------------------------------------
create or replace function public.reroll_today(p_date date)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_uid uuid := auth.uid(); v_day date := kst_day(); e daily_entries; v_id text;
        -- e daily_entries: daily_entries 한 행을 통째로 담는 변수 (e.reroll_count처럼 쓴다)
begin
  if v_uid is null then raise exception 'UNAUTHENTICATED'; end if;
  if p_date is distinct from v_day then raise exception 'DAY_CHANGED'; end if;
  -- 오늘 행을 잠그고 읽는다. 두 탭에서 동시에 눌러도 한 번에 하나씩만 처리되어 횟수가 꼬이지 않는다
  select * into e from daily_entries where user_id = v_uid and date = v_day for update;
  if not found then raise exception 'NOT_DRAWN'; end if;                      -- 아직 뽑기 전
  if e.completed_at is not null then raise exception 'ALREADY_COMPLETED'; end if;  -- 이미 완료
  if e.reroll_count >= 3 then raise exception 'NO_REROLLS'; end if;          -- 3번 다 씀
  v_id := pick_mission(v_uid, v_day, e.seen_mission_ids);  -- 오늘 본 것들을 빼고 뽑기
  update daily_entries
     set current_mission_id = v_id,                    -- 지금 카드 교체
         seen_mission_ids = seen_mission_ids || v_id,  -- ||: 배열 끝에 추가 (JS의 push)
         reroll_count = reroll_count + 1
   where user_id = v_uid and date = v_day;
  return today_state(v_uid, v_day);
end $$;


-- ------------------------------------------------------------
-- complete_today(화면이 아는 날짜)  ← POST /api/today/complete
--   오늘 미션을 완료 처리하고 도장 6종 중 하나를 무작위로 정한다. 취소는 없다
-- ------------------------------------------------------------
create or replace function public.complete_today(p_date date)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_uid uuid := auth.uid(); v_day date := kst_day(); e daily_entries;
begin
  if v_uid is null then raise exception 'UNAUTHENTICATED'; end if;
  -- 23:59에 누른 완료가 00:00대에 도착해도 kst_day()가 전날이라 통과한다
  if p_date is distinct from v_day then raise exception 'DAY_CHANGED'; end if;
  select * into e from daily_entries where user_id = v_uid and date = v_day for update;  -- 연타 방지용 잠금
  if not found then raise exception 'NOT_DRAWN'; end if;
  if e.completed_at is not null then raise exception 'ALREADY_COMPLETED'; end if;
  update daily_entries
     set completed_at = now(),
         -- random()은 0 이상 1 미만 → ×6 후 내림하면 0~5 → +1 하면 1~6번째 (SQL 배열은 1부터 시작)
         stamp_id = (array['p01','p02','p03','p04','p05','p06'])[1 + floor(random() * 6)::int]
   where user_id = v_uid and date = v_day;
  return today_state(v_uid, v_day);
end $$;


-- ------------------------------------------------------------
-- get_month(그 달 1일)  ← GET /api/records?month=2026-09
--   Route Handler가 '2026-09'를 '2026-09-01'로 바꿔 넘긴다.
--   그 달에 완료한 날들과, 처음 앱을 쓴 달(이전 달 화살표를 막는 데 씀)을 돌려준다
-- ------------------------------------------------------------
create or replace function public.get_month(p_month date)
returns jsonb language sql stable security definer set search_path = public as $$
  select jsonb_build_object(
    'month', to_char(p_month, 'YYYY-MM'),                     -- to_char: 날짜를 문자열 형식으로
    'firstMonth', (select to_char(min(date), 'YYYY-MM') from daily_entries where user_id = auth.uid()),
    'days', coalesce((
      -- jsonb_agg: 여러 행을 JSON 배열 하나로 묶는다 (날짜순)
      select jsonb_agg(jsonb_build_object('date', e.date, 'missionText', m.text,
               'stampId', e.stamp_id, 'completedAt', e.completed_at) order by e.date)
      from daily_entries e join missions m on m.id = e.current_mission_id
      where e.user_id = auth.uid() and e.completed_at is not null      -- 본인, 완료한 날만
        and e.date >= p_month and e.date < (p_month + interval '1 month')::date  -- 그 달 1일~말일
    ), '[]'::jsonb)                                              -- 없으면 빈 배열
  )
$$;
```

### 부록: 4단계(보류) SQL

미션 제출·관리자 기능을 만들 때만 실행한다. 위 1~7을 실행한 뒤 A → B → C 순서로 실행하고, 만들지 않으면 건너뛴다.

**A. 문구 비교 도우미, 테이블, 접근 규칙, 관리자 확인 함수**

```sql
-- 중복 비교용: 공백·문장부호 제거, 소문자
create or replace function public.normalize_text(t text)
returns text language sql immutable as $$
  select lower(regexp_replace(t, '[[:space:][:punct:]]', '', 'g'))
$$;

create table public.submissions (
  id              uuid primary key default gen_random_uuid(),
  user_id         uuid not null references auth.users (id) on delete cascade,
  text            text not null check (char_length(text) between 5 and 40),
  normalized_text text generated always as (public.normalize_text(text)) stored,
  difficulty      text not null check (difficulty in ('easy', 'challenge')),
  status          text not null default 'pending'
                  check (status in ('pending', 'approved', 'rejected')),
  mission_id      text references public.missions (id),
  created_day     date not null default public.kst_day(),  -- 하루 3개 제한용
  created_at      timestamptz not null default now(),
  reviewed_at     timestamptz,
  unique (user_id, normalized_text)
);
create index submissions_status_idx on public.submissions (status, created_at desc);
create index submissions_user_idx on public.submissions (user_id, created_at desc);

create table public.admins (
  user_id uuid primary key references auth.users (id) on delete cascade
);

create sequence public.user_mission_seq start 1;  -- 승인된 제출의 S번호

alter table public.submissions enable row level security;
alter table public.admins      enable row level security;

create policy "submissions: 본인 제출 읽기" on public.submissions
  for select to authenticated using (user_id = (select auth.uid()));

-- submissions도 쓰기 정책 없이 아래 함수로만 쓴다.
-- admins는 정책이 없어 아무도 직접 읽지 못한다.

-- ------------------------------------------------------------
-- is_admin(): 지금 로그인한 사람이 관리자인가?
--   · admins 표에 내 id가 있으면 true, 없으면 false
--   · 관리자 함수(admin_*)들이 맨 앞에서 이 값으로 검사한다
--   · admins 표에는 RLS 정책이 없어 아무도 직접 못 읽으므로 security definer가 필요하다
-- ------------------------------------------------------------
create or replace function public.is_admin()
returns boolean language sql stable security definer set search_path = public as $$
  select exists (select 1 from admins where user_id = auth.uid())  -- 한 행이라도 있으면 true
$$;
```

제출 중복은 공백·문장부호·대소문자를 무시하고 비교한다. 내가 이미 낸 문구와 기존 미션 문구가 비교 대상이고, 다른 사람의 제출은 비교하지 않는다.

**B. API가 부르는 함수**

```sql
-- ------------------------------------------------------------
-- submit_mission(문구, 난이도)  ← POST /api/submissions
--   사용자가 새 미션을 제안한다. missions가 아니라 submissions에 '대기'로 들어간다
-- ------------------------------------------------------------
create or replace function public.submit_mission(p_text text, p_difficulty text)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_uid uuid := auth.uid(); v_day date := kst_day(); v_text text := btrim(p_text);
        v_count int; v_id uuid;                       -- btrim: 앞뒤 공백 제거
begin
  if v_uid is null then raise exception 'UNAUTHENTICATED'; end if;
  -- 입력 검사: 5~40자, 난이도는 easy/challenge만
  if v_text is null or not (char_length(v_text) between 5 and 40)
     or coalesce(p_difficulty, '') not in ('easy', 'challenge') then
    raise exception 'INVALID_INPUT';
  end if;
  -- 같은 사용자의 동시 제출을 한 줄로 세운다 (연타로 3개 제한을 넘지 못하게)
  perform pg_advisory_xact_lock(hashtext(v_uid::text));
  select count(*) into v_count from submissions where user_id = v_uid and created_day = v_day;
  if v_count >= 3 then raise exception 'DAILY_LIMIT'; end if;      -- 오늘 3개 초과
  -- 기존 미션과 같은 문구(공백·문장부호·대소문자 무시)면 거절
  if exists (select 1 from missions where normalize_text(text) = normalize_text(v_text)) then
    raise exception 'DUPLICATE';
  end if;
  insert into submissions (user_id, text, difficulty, created_day)
  values (v_uid, v_text, p_difficulty, v_day) returning id into v_id;  -- returning: 방금 만든 행의 id 받기
  return jsonb_build_object('id', v_id, 'status', 'pending', 'todayCount', v_count + 1);
exception when unique_violation then
  -- 내가 이미 낸 같은 문구 (submissions의 unique(user_id, normalized_text))
  raise exception 'DUPLICATE';
end $$;


-- ------------------------------------------------------------
-- admin_list_submissions(상태)  ← GET /api/admin/submissions?status=pending
--   관리자 화면용: 상태별 개수와 해당 상태의 제출 목록
-- ------------------------------------------------------------
create or replace function public.admin_list_submissions(p_status text default 'pending')
returns jsonb language plpgsql stable security definer set search_path = public as $$
begin
  if not is_admin() then raise exception 'FORBIDDEN'; end if;      -- 관리자만
  return jsonb_build_object(
    -- jsonb_object_agg(키, 값): { "pending": 3, "approved": 12, ... } 모양으로 묶기
    'counts', coalesce((select jsonb_object_agg(status, n)
                        from (select status, count(*) as n from submissions group by status) c), '{}'::jsonb),
    'items', coalesce((select jsonb_agg(jsonb_build_object('id', id, 'text', text,
               'difficulty', difficulty, 'createdAt', created_at) order by created_at desc)
             from submissions where status = p_status), '[]'::jsonb)
  );
end $$;


-- ------------------------------------------------------------
-- admin_approve(제출 id, 고친 문구?, 고친 난이도?)  ← POST /api/admin/submissions/[id]/approve
--   승인하면 missions에 S번호로 새 행을 만들고, 다음 뽑기부터 후보가 된다.
--   문구·난이도를 안 넘기면(null) 제출된 값을 그대로 쓴다
-- ------------------------------------------------------------
create or replace function public.admin_approve(p_id uuid, p_text text default null, p_difficulty text default null)
returns jsonb language plpgsql security definer set search_path = public as $$
declare s submissions; v_text text; v_diff text; v_mid text;
begin
  if not is_admin() then raise exception 'FORBIDDEN'; end if;
  -- 대기 중인 제출만, 잠그고 읽는다 (같은 제출을 두 번 승인하는 것을 막음)
  select * into s from submissions where id = p_id and status = 'pending' for update;
  if not found then raise exception 'NOT_FOUND'; end if;
  v_text := coalesce(nullif(btrim(p_text), ''), s.text);   -- nullif(a, ''): a가 빈 문자열이면 null
  v_diff := coalesce(p_difficulty, s.difficulty);
  if v_diff not in ('easy', 'challenge') then
    raise exception 'INVALID_INPUT';
  end if;
  -- 시퀀스에서 다음 번호를 받아 'S' + 4자리(앞을 0으로 채움)로 만든다 → S0001, S0002 ...
  v_mid := 'S' || lpad(nextval('user_mission_seq')::text, 4, '0');
  insert into missions (id, text, difficulty, source) values (v_mid, v_text, v_diff, 'user');
  update submissions set status = 'approved', mission_id = v_mid, reviewed_at = now()
   where id = p_id;
  return jsonb_build_object('missionId', v_mid);
end $$;


-- ------------------------------------------------------------
-- admin_reject(제출 id)  ← POST /api/admin/submissions/[id]/reject
--   대기 중인 제출을 반려한다. missions에는 아무것도 추가하지 않는다
-- ------------------------------------------------------------
create or replace function public.admin_reject(p_id uuid)
returns jsonb language plpgsql security definer set search_path = public as $$
begin
  if not is_admin() then raise exception 'FORBIDDEN'; end if;
  update submissions set status = 'rejected', reviewed_at = now()
   where id = p_id and status = 'pending';
  if not found then raise exception 'NOT_FOUND'; end if;   -- 없거나 이미 처리된 제출
  return jsonb_build_object('status', 'rejected');
end $$;
```

## Supabase 설정 체크리스트

위에서부터 순서대로 하면 배포 전까지 끝난다. 대시보드 메뉴 이름은 Supabase 개편에 따라 조금 다를 수 있다.

### 1. 프로젝트

- [ ] 새 프로젝트 만들기. 리전은 서울(Northeast Asia, Seoul)로 고른다
- [ ] DB 비밀번호를 비밀번호 관리자에 저장한다

### 2. 인증

- [ ] Authentication의 로그인 방식(Providers) 설정에서 익명 로그인(Anonymous sign-ins)을 켠다
- [ ] 익명 가입 남용 방지: IP당 시간당 30회 기본 제한을 확인하고, 필요하면 Cloudflare Turnstile 또는 hCaptcha를 켠다. 켜면 클라이언트의 `signInAnonymously()`에 `captchaToken`을 넘겨야 한다
- [ ] URL 설정: Site URL과 Redirect URLs에 `http://localhost:3000`과 Vercel 도메인을 넣는다

### 3. 데이터베이스

- [ ] SQL Editor에서 '테이블 SQL 초안' 1~6을 순서대로 실행한다(부록은 4단계를 만들 때만)
- [ ] 7(시드)을 실행하고 easy 180개, challenge 20개인지 확인한다
- [ ] Table Editor에서 테이블 2개(missions, daily_entries) 모두 RLS가 켜져 있는지 확인한다

### 4. 키와 환경변수

| 변수 | 값 | 넣는 곳 |
|---|---|---|
| NEXT_PUBLIC_SUPABASE_URL | Project URL | .env.local, Vercel |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | publishable 키(`sb_publishable_…`, 예전 이름은 anon 키) | .env.local, Vercel |

비밀 키(secret, 예전 이름 service_role)는 RLS를 건너뛰므로 이 설계에서는 쓰지 않는다. 나중에 쓰게 되더라도 `NEXT_PUBLIC_` 접두사를 붙이지 않는다. 붙이면 브라우저 코드에 포함된다.

- [ ] `.env.local`이 `.gitignore`에 들어 있는지 확인한다
- [ ] Vercel 프로젝트의 Environment Variables에 같은 값을 등록한다

### 5. 개발 편의

- [ ] 타입 생성: `npx supabase gen types typescript --project-id <프로젝트 ID> > types/database.ts`(이 저장소는 `src/` 없이 루트에 둔다). Supabase CLI 로그인이 필요하고, `supabase.rpc()`의 함수 이름과 인자가 자동완성된다. SQL을 바꿀 때마다 다시 만든다

### 6. 동작 확인

- [ ] 익명 사용자 A: 뽑기 → 재뽑기 3회 → 4번째는 NO_REROLLS → 완료 → 다시 완료하면 ALREADY_COMPLETED
- [ ] 익명 사용자 B로 A의 기록이 조회되지 않는지
- [ ] 내부 함수 `pick_mission`을 직접 부르면 권한 오류가 나는지

SQL 초안은 로컬 Postgres 16에서 `auth.uid()`와 역할을 흉내 내 확인했다. 핵심 1~7만 실행해도 위 흐름과 에러 코드가 모두 동작하고, 부록을 이어서 실행하면 제출·승인·반려도 동작한다. Supabase에서도 이 목록으로 한 번 더 확인한다.

### 7. 운영

무료 프로젝트는 7일 동안 요청이 거의 없으면 일시 중지된다. 중지 약 1주 전에 메일이 오고, 중지돼도 1년 안에는 대시보드에서 복구할 수 있다. 하루 몇 번의 요청이면 중지되지 않는다.

### 8. 4단계를 만들 때 추가할 설정

4단계(미션 제출·관리자)를 만들지 않으면 이 항목은 모두 건너뛴다.

- [ ] Email 로그인을 켠다(관리자용). 관리자 계정은 Authentication > Users에서 직접 추가한다. 권한은 admins 테이블로만 판단하므로 다른 이메일 계정이 생겨도 관리자 기능은 못 쓴다
- [ ] SQL Editor에서 '부록: 4단계(보류) SQL'의 A → B → C를 실행한다
- [ ] 관리자 등록: `insert into public.admins (user_id) values ('<Users에서 복사한 관리자 UUID>');`
- [ ] Table Editor에서 submissions·admins의 RLS가 켜져 있는지 확인한다
- [ ] 관리자가 아닌 계정으로 /api/admin 요청 시 FORBIDDEN이 나는지 확인한다
