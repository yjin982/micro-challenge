# 추가 기능 계획: 완료 메모, 미션 제출

2026-10-27 작성, 같은 날 결정 반영(1-8, 2-5. 2차: 처리방침 알림 추천안, 메모 2,000자 상한과 글자 수 표시, 마스코트 없음, 미션 제안하기는 '피드백 보내기' 위). 로그인 흐름 개편을 `main`에 합친 뒤(커밋 `e6ed5b6`)의 다음 작업이다. 순서는 **1. 완료 메모 → 2. 미션 제출**이다. 2는 1을 마친 뒤 만든다(2026-10-27 결정). 기록 모아 보기([로그인 계획](로그인-흐름-계획.md) 10단계)는 이 문서와 따로다.

아직 구현 전이다. 화면 설계 보드 → DB → API → 화면 순서로 진행한다.

## 1. 완료 메모(미션을 마치며 한 줄 남기기)

### 1-1. 왜 필요한가

지금은 '완료했어요!'를 누르면 바로 도장이 찍힌다. 몸을 쓰는 미션은 그걸로 충분하지만, 머릿속에서 끝나는 미션은 해냈다는 감각이 약하다.

- 인지/생각: "10초 동안 아무 생각 안 하기 도전"(E088). 해 봤는지, 어땠는지 남길 곳이 없다
- 감정/자기표현: "지금 기분 한 단어로 표현"(E091), "나에게 '요즘 뭐가 제일 좋아?' 물어보기"(E101). 떠올린 단어나 답을 적어야 완료한 느낌이 난다
- 몸/행동: "팔꿈치를 구부렸다 펴기"(E029)도 느낌이나 한 방법을 적어 둘 수 있다

그래서 완료할 때 짧은 글을 남길 수 있게 한다. **쓰지 않아도 완료된다.** 미션 200개는 7개 분류(몸/행동, 인지/생각, 감정/자기표현, 환경 상호작용, 이상한 행동/밈, 디지털/습관 각 30개, 도전적 20개)에 걸쳐 있으므로, 대화상자의 제목과 안내는 어느 분류에도 어색하지 않게 하고, 분류에 맞춘 예시는 입력창 자리 글(placeholder)에만 쓴다.

### 1-2. 동작

#### 홈에서 완료할 때

```text
도전중 카드 → '완료했어요!' → 메모 대화상자
   ├─ (쓰거나 비워 두고) '완료하기' 또는 Enter → 완료 요청(메모 포함) → 대화상자 닫힘 → 지금과 같은 도장 연출
   └─ '취소' / Esc / 바깥 → 대화상자만 닫힘(완료되지 않음, 쓰던 글은 버린다)
```

- 메모는 비워도 된다. 앞뒤 공백만 있으면 비운 것으로 본다
- 줄바꿈은 받지 않는다. Enter는 '완료하기'와 같다. 붙여 넣은 글의 줄바꿈은 공백 하나로 바꾼다
- 글자 수 상한은 **2,000자**다. 입력창 아래에 `0 / 2000`처럼 글자 수를 보여준다. 2,000자를 넘으면 입력창 테두리가 빨간색으로 바뀌고 주 버튼이 비활성이 되어 제출할 수 없다. 2,000자 이내면 그대로 제출된다. 입력 자체는 막지 않는다(붙여 넣은 뒤 줄여서 낼 수 있게). 입력창은 긴 글을 화면 안에서 줄을 감아 보여준다
- 완료 요청이 실패하면(인터넷, `DAY_CHANGED` 등) 대화상자를 닫지 않고 안에 안내한다. 쓰던 글이 남아 있어야 한다
- 완료 취소는 여전히 없다. 메모를 지워도 완료는 그대로다
- 모바일 스와이프는 다시 뽑기만 하므로 그대로 둔다
- 완료 뒤 홈의 완료 카드(모바일 완료 화면, 데스크톱 왼쪽 도장 카드)에 메모를 보여준다. 연속 달성 화면과 최근 기록에는 보여주지 않는다(2026-10-27 결정)

#### 기록 화면(`/records`)에서

- 완료한 날의 상세 카드에 메모를 보여준다
- 메모가 있으면 '수정', '삭제'. 없으면 '한 줄 남기기'(완료한 날이면 지난 날도 나중에 쓸 수 있다)
- 수정·한 줄 남기기는 **완료할 때와 같은 대화상자**를 쓴다(2026-10-27 결정). 버튼만 '완료하기' 대신 '저장'
- 삭제는 확인을 한 번 묻는다
- 고칠 수 있는 것은 **메모 글뿐**이다. 미션, 완료 시각, 도장, 완료 여부는 바꿀 수 없다
- 완료하지 않은 날(오늘 도장 전, 쉬어 간 날)에는 메모가 없다
- 오늘 메모를 기록 화면에서 고치면 홈에 돌아갔을 때 새 내용이 보여야 한다(홈은 들어올 때 오늘 상태를 다시 불러온다)

### 1-3. 문구와 마스코트(결정)

제목·안내는 공통, 자리 글만 분류별이다.

| 자리 | 문구 |
| --- | --- |
| 제목 | 오늘의 기적, 한 줄 남겨 볼까요? |
| 안내 | 떠오른 답, 해 본 느낌, 한 방법… 무엇이든 좋아요. 비워 둬도 완료돼요. |
| 주 버튼 | 완료하기(기록 화면에서는 저장). 2,000자를 넘으면 비활성 |
| 글자 수 | 입력창 아래 오른쪽 `0 / 2000`. 넘으면 숫자와 입력창 테두리가 빨간색(`sunday`) |
| 보조 | 취소 |
| 기록 상세(메모 없음) | 한 줄 남기기 |
| 삭제 확인 | 이 메모를 지울까요? / 미션 완료와 도장은 그대로예요. |

입력창 자리 글(분류별, `missions.category`):

| 분류 | 자리 글 |
| --- | --- |
| 몸/행동 | 예) 왼팔이 더 뻐근했다 |
| 인지/생각 | 예) 생각보다 10초가 길었다 |
| 감정/자기표현 | 예) 설렘 |
| 환경 상호작용 | 예) 창밖 나무가 생각보다 초록이었다 |
| 이상한 행동/밈 | 예) 혼자 웃음이 터졌다 |
| 디지털/습관 | 예) 알림 3개를 껐다 |
| 도전적 | 예) 두 번 만에 해냈다 |
| 분류 없음(나중에 들어올 제출 미션) | 예) 해 보니 생각보다 쉬웠다 |

- 자리 글은 코드의 표(분류 → 문구)로 둔다. 분류가 표에 없으면 '분류 없음' 문구
- 마스코트: **넣지 않는다**(2026-10-27 결정). 나중에 넣는다면 아직 쓰지 않는 포즈 중 `excited`(두 팔을 들고 신난 티라노)나 `favorite`(쿠키)

### 1-4. DB 설계(결정: 컬럼 추가)

`daily_entries`에 컬럼을 더한다. 새 테이블을 만들지 않는다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| **가. `daily_entries`에 `note`, `note_updated_at` 추가(채택)** | 완료와 1:1이라 구조가 단순하다. 기존 RLS("본인 행 읽기"), 계정 삭제 cascade, `get_month` 조회를 그대로 쓴다 | 메모 이력(예전 글)은 남지 않는다 |
| 나. 새 테이블 `entry_notes(user_id, date, note, …)` | 메모만 따로 관리·확장(여러 개, 이력)하기 쉽다 | RLS·외래 키·조인이 늘어난다. 하루 한 개라 얻는 것이 적다 |

```sql
-- 새 마이그레이션(예: 2026MMDD000000_entry_note.sql). SQL Editor에서 실행한다
alter table public.daily_entries
  add column note text check (note is null or (note <> '' and note !~ '[\r\n]' and char_length(note) <= 2000)),
  add column note_updated_at timestamptz,
  -- 메모는 완료한 날에만
  add constraint daily_entries_note_needs_completion check (note is null or completed_at is not null);

-- 입력 정리: 줄바꿈(\r\n, \r, \n)과 탭을 공백 하나로, 연달은 공백은 하나로, 앞뒤 공백 제거, 비면 null
create or replace function public.clean_note(p text)
returns text language sql immutable as $$
  select nullif(btrim(regexp_replace(coalesce(p, ''), '[\s]+', ' ', 'g')), '')
$$;
```

- 길이 상한 2,000자(2026-10-27 결정). 화면이 막고(1-2), DB 함수가 정리한 글(`clean_note` 결과)이 2,000자를 넘으면 `INVALID_INPUT`, 제약이 마지막으로 막는다. 화면을 거치지 않고 API로 아주 긴 글을 넣는 남용도 이것으로 막힌다
- 글자 수는 Postgres `char_length`(유니코드 문자 단위)와 같게 센다. 화면에서 `value.length`(UTF-16 단위)를 쓰면 이모지가 2자로 세어져 둘이 어긋나므로 `[...value].length`(코드 포인트)로 센다
- 줄바꿈은 받지 않는다. 화면이 막고, DB 함수(`clean_note`)가 한 번 더 공백으로 바꾸고, 제약이 마지막으로 막는다
- 화면은 글자로만 그린다(React가 이스케이프한다). HTML로 넣지 않는다
- 계정 삭제·익명 정리(180일) 때 행과 함께 지워진다. 따로 할 일이 없다

### 1-5. DB 함수와 API

| 바뀌는 것 | 내용 |
| --- | --- |
| `complete_today(p_date date, p_note text default null)` | 기존 함수를 지우고(`drop function public.complete_today(date)`) 인자를 더해 다시 만든다. 인자가 바뀌면 Postgres는 다른 함수로 보므로 지우지 않으면 두 개가 생긴다. 기본값이 있어 메모 없이 부르던 화면도 그대로 동작한다. 실행 권한(`revoke`/`grant`)도 새 서명으로 다시 준다 |
| `set_note(p_date date, p_note text)` 새 함수 | 본인(`auth.uid()`)의, **완료한** 날의 메모만 고친다. `clean_note` 결과가 null이면 삭제. 행이 없거나 완료 전이면 `NOT_FOUND`. 돌려주는 값 `{ date, note, noteUpdatedAt }` |
| `today_state` | `note`(오늘 메모, 홈 완료 카드용)와 `mission.category`(자리 글용)를 더한다 |
| `get_month` | `days[]`에 `note`, `category`(수정 대화상자의 자리 글용)를 더한다 |

| API | 요청 | 응답 |
| --- | --- | --- |
| `POST /api/today/complete`(기존) | `{ date, note? }` | 지금과 같은 오늘 상태(+ `note`) |
| `PATCH /api/records/note`(새, 7번째 API) | `{ date: "YYYY-MM-DD", note: string \| null }`. `null`이나 빈 글이면 삭제 | `{ date, note, noteUpdatedAt }` |

- 기존 규칙 그대로: Route Handler → `supabase.rpc()` → security definer 함수. 테이블 쓰기 정책은 두지 않는다
- `types/api.ts`(`TodayState.note`, `Mission.category`, `MonthRecords.days[].note·category`, 새 응답 타입), `ErrorCode`에 `NOT_FOUND`(404), `lib/api-error.ts` 문구, `handleRpc`가 받는 함수 목록, `pnpm gen:types`
- 확인 SQL `supabase/tests/entry-note.sql`(`delete-account.sql`처럼 임시 사용자로 확인 후 되돌림): 메모와 함께 완료, 빈 메모·공백만은 null, 줄바꿈이 공백으로 바뀜, 2,000자는 통과·2,001자는 `INVALID_INPUT`, 완료 전 날·없는 날은 `NOT_FOUND`, 삭제, 다른 사용자 행은 못 고침, 완료 안 한 행에 메모를 넣으면 제약에 걸림, 메모 없이 부르던 `complete_today(p_date)`도 동작

### 1-6. 화면 컴포넌트

| 컴포넌트 | 위치 | 내용 |
| --- | --- | --- |
| `NoteDialog` | `components/ui/` 또는 `components/home/` | 완료·수정·한 줄 남기기가 함께 쓰는 대화상자. 공통 제목·안내(마스코트 없음), 입력창(분류별 자리 글), 글자 수 `n / 2000`, 주 버튼('완료하기'/'저장', 2,000자를 넘으면 비활성), 취소, 실패 안내 |
| 홈 완료 연결 | `components/home/` | '완료했어요!' → `NoteDialog` → `api.complete(date, note)` → 지금의 도장 연출(`celebrate`) |
| 홈 완료 카드의 메모 | `components/home/DoneCard.tsx` 등 | 메모가 있으면 미션 문구 아래에 보여준다(없으면 아무것도 없음) |
| 기록 상세의 메모 | `components/records/RecordDetail.tsx` | 메모 보기, 한 줄 남기기·수정(`NoteDialog`)·삭제 |
| 삭제 확인 | `SketchDialog` | 첫 포커스는 "취소"(`data-autofocus`), 지우기는 빨간 버튼(`Button` `danger`) |

- 입력창: 줄바꿈을 받지 않지만 긴 글이 한 줄 `input`에서 옆으로 밀려 안 보이지 않도록, 줄을 감아 보여주는 `textarea`(높이 자동)에서 Enter를 '제출'로 바꾸고 붙여 넣은 줄바꿈을 공백으로 바꾸는 방식을 쓴다. 한글 입력 조합 중의 Enter(`isComposing`)는 제출로 보지 않는다
- 열리면 입력창에 포커스(완료할 때 바로 쓸 수 있게). 라벨은 안내 문구와 연결한다
- 글자 수: 입력창 아래 오른쪽에 `n / 2000`(`aria-live="polite"`로 넘었을 때 알림). 넘으면 숫자와 테두리를 빨간색으로, 입력창에 `aria-invalid`, 주 버튼 `disabled`. Enter로 제출할 때도 같은 조건을 본다
- 지금의 [SketchDialog](../components/ui/SketchDialog.tsx)는 마스코트를 꼭 받는다. 마스코트를 선택(없으면 그리지 않음)으로 바꾸고, 입력창을 children으로 넣어 첫 포커스를 입력창에 준다(`data-autofocus`)
- 모바일 화면 키보드가 올라오면 대화상자가 가려지지 않게(`dvh`, 입력창 쪽으로 스크롤) 확인한다

### 1-7. 처리방침 변경과 알림(추천)

사용자가 직접 쓴 글을 새로 저장하므로 [처리방침](../components/legal/documents.ts)을 고친다.

- 1절 '서비스 이용 기록'에 "미션을 마치며 직접 남긴 메모(남긴 경우)"를 더한다
- "메모는 본인만 볼 수 있고, 문의에 답하거나 법에 따라야 하는 경우 말고는 운영자가 열어 보지 않습니다" 한 줄

**알림 방법(2026-10-27 추천안으로 결정): 메모 기능을 배포하는 날 처리방침도 함께 바꾸고(시행일 = 배포일), 홈에 7일 동안 닫을 수 있는 짧은 안내를 띄운다.** 함께 9절 문구를 실제 운영에 맞게 고친다.

- 9절(지금): "내용이 바뀌면 시행 7일 전부터 서비스 안에서 알립니다"
- 9절(제안): "내용이 바뀌면 서비스 안에서 알립니다. 수집하는 정보가 늘거나 이용자에게 불리하게 바뀌는 경우에는 시행 7일 전부터 알립니다"
- 이유: 메모는 이용자가 쓰고 싶을 때만 남기는 선택 항목이라 이용자에게 불리한 변경이 아니고, 아직 정식 공개 전(Google 앱 '테스트 중')이다. 7일을 기다리며 기능 배포를 미루는 것보다 배포와 함께 알리는 쪽이 낫다
- 지금 9절이 "7일 전"이라고 약속하고 있으므로, **9절 문구를 고치는 것 자체**를 이번 변경에 넣는다(보수적인 방법인 '7일 먼저 바꾸고 기능은 나중에 열기'는 쓰지 않는다)
- 안내: 홈 위쪽 한 줄 "개인정보처리방침이 바뀌었어요(완료 메모 추가) · 보기" + 닫기. 닫은 것은 브라우저에 기억한다(`localStorage`, 기기마다). 시행일 7일 뒤에는 코드에서 띄우지 않는다
- 이 판단은 법률 자문이 아니다. 정식 공개 전에 한 번 더 확인한다

### 1-8. 결정(2026-10-27)

1. 글자 수: **2,000자 상한**. 입력창 아래 `0 / 2000`, 넘으면 테두리 빨간색 + 주 버튼 비활성(제출 불가), 서버도 같은 상한(처음에는 '제한 없음'이었다가 같은 날 바꿨다)
2. 줄바꿈: **받지 않음**(Enter = 완료하기, 붙여 넣은 줄바꿈은 공백)
3. 문구: 1-3의 공통 제목·안내, **분류별 예시는 자리 글에만**
4. 마스코트: **넣지 않는다**
5. 기록 화면 수정: **완료 대화상자와 같은 모양**
6. 메모를 보여줄 곳: **기록 상세, 홈 완료 카드**. 연속 달성·최근 기록에는 보이지 않음
7. 처리방침 알림: **1-7의 추천안**(배포와 함께 변경 + 홈에 7일 안내 + 9절 문구 수정)

## 2. 미션 제출(완료 메모 다음에 만든다)

기획서·서버 설계의 '4단계(보류)'와 화면 설계 보드 34(설정 · 미션 제출), 35(관리자 · 제출 미션 검토)가 출발점이다. 그 설계는 **로그인 개편 전**(자동 익명 + 관리자 이메일 계정)을 가정하고 있어, 지금 구조와 2026-10-27 결정에 맞게 고칠 점을 정리한다.

### 2-1. 기존 설계 요약(서버 설계 부록 A~C)

- `submissions`(id, user_id → `auth.users` on delete cascade, text 5~40자, `normalized_text`(공백·문장부호 제거, 소문자), difficulty, status pending/approved/rejected, mission_id, created_day, created_at, reviewed_at, `unique(user_id, normalized_text)`)
- `admins(user_id)`, `is_admin()`, 승인 번호 시퀀스 `user_mission_seq`(S0001…)
- 함수: `submit_mission`(하루 3개, 기존 미션·내 제출과 중복 거절), `admin_list_submissions`, `admin_approve`(문구·난이도 고쳐서 승인 → `missions`에 S번호로 추가, `source = 'user'`), `admin_reject`
- RLS: submissions는 본인 행 읽기만, 쓰기는 함수로만. admins는 정책 없음
- API 5개: `GET/POST /api/submissions`, `GET /api/admin/submissions`, `POST …/[id]/approve`, `POST …/[id]/reject`

### 2-2. 지금 구조에 맞게 고칠 점

| 항목 | 기존 가정 | 바꿀 점 |
| --- | --- | --- |

### 2-3. 처리방침·약관에 더할 것

- 처리방침 1절: 제출한 미션 문구, 처리 상태, 반려 사유
- 약관: 제출한 문구는 승인되면 서비스의 미션으로 다른 이용자에게 보이고, 운영자가 고칠 수 있으며, 계정을 지워도 미션으로 남는다(약관 7절 '미션 문구의 권리는 운영자에게'와 맞춘다). 개인정보나 남을 불편하게 하는 내용은 반려한다
- 변경 알림은 1-7과 같은 방식(수집하는 정보가 늘므로 9절 제안 문구대로라면 7일 전 안내 대상이다. 미션 제출을 열기 7일 전에 처리방침·약관을 먼저 바꾼다)
- 미션 작성 기준(기획서): 혼자, 도구 없이, 1분 안쪽, 끝나는 순간이 분명할 것(보드 35 아래 안내). 제출 화면에도 보여준다
